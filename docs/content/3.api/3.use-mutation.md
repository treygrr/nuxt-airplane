```ts
function useMutation<N extends MutationName>(
  name: N,
  options?: { queue?: true }
): UseMutationReturn<MutationInput<N>, MutationRow>

function useMutation<N extends MutationName>(
  name: N,
  options: { queue: false }
): UseMutationReturn<MutationInput<N>, MutationResult<N>>
```

## Parameters

| | |
| --- | --- |
| `name` | A mutation document name from `NuxtAirplaneMutations`. |
| `options.queue` | `false` sends the mutation directly instead of queuing it; see [Online-only mutations](/guide/mutations#online-only-mutations). Default `true`. |

## Returns

```ts
interface UseMutationReturn<V, R> {
  mutate: (variables: V) => Promise<R>
  loading: Ref<boolean>
  error: Ref<Error | null>
}

/** The mutation's variables, and any of its handler's local variables. */
type MutationInput<N> = MutationVariables<N> & Partial<Omit<MutationLocals<N>, keyof MutationVariables<N>>>

interface MutationRow {
  id: number
  document: string
  /** What is sent: the variables the mutation declares. */
  variables: unknown
  /** The handler's local variables it was queued with, defaults filled in. Never sent. */
  local?: Record<string, unknown>
  /** From the handler's `describe`, or the humanized document name. */
  description: string
  status: 'pending' | 'syncing' | 'failed'
  createdAt: number
  error?: string
  /** Sent with every attempt, so the server can tell a retry from a new mutation. */
  idempotencyKey?: string
  /** How many times it has been sent. */
  attempts?: number
  /** Outbox ids it depends on, and ids it only has to come after. */
  dependsOn?: number[]
  after?: number[]
  // …and the module's own bookkeeping: keys, rows, unkeyed, tempIds, creates, writes.
}
```

`mutate` takes the mutation's variables and any [local variables](/guide/mutation-handlers#local) its handler declares; only the first are sent. It resolves once the change is applied locally and queued; see [Mutations](/guide/mutations). When the handler's [`merge`](/guide/mutation-handlers#merge) folded it into a mutation already waiting, it resolves with that row. It rejects if `describe` or `apply` throws, if the name is not a mutation's, if the browser has no room for the write, or if `mutate` is called on the server.

`loading` is `true` from the call until `apply` has run. Bind it to the button that calls `mutate`, as both its loading and disabled state, so a quick second press cannot queue the change twice; see [One press, one mutation](/guide/mutations#one-press-one-mutation).

With `queue: false`, `mutate` resolves with the mutation's result type once the server has answered, `loading` is `true` while the request is in flight, and it rejects while offline or when the server returns errors.

## Example

```vue
<script setup lang="ts">
const setOnHand = useMutation('UpdateSiteItemOnHand')

function onChange(siteId: string, itemId: string, onHand: number) {
  setOnHand.mutate({ siteId, itemId, onHand })
}
</script>
```

Direct, for a mutation whose response the UI needs:

```vue
<script setup lang="ts">
const checkout = useMutation('Checkout', { queue: false })

async function pay() {
  const { checkout: order } = await checkout.mutate({ cartId })
  await navigateTo(`/orders/${order.id}`)
}
</script>
```
