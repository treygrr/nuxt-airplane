```ts
function defineAirplaneStores(
  stores: Record<string, string>,
  options?: { version?: number }
): AirplaneStores
```

Default-export its result from a file in the [`handlers.dir`](/getting-started/configuration#handlersdir). Several files can declare stores; they are merged and the highest `version` wins.

Every type your documents select with an `id` already has a table named after it (`db.Site`), keyed on the id and typed from the fields your documents select; see [Inferred tables](/guide/stores-and-query-handlers#inferred-tables). This helper adds to that. Only the inferred tables your app mentions are created, and naming one here counts: `SiteItem: ''` creates it with no extra index.

## Parameters

| | |
| --- | --- |
| `stores` | For an inferred table, the extra indexes: `Item: 'name'`. For a table of your own, its full definition in Dexie's [`stores()` syntax](https://dexie.org/docs/Version/Version.stores()): `'++id, siteId'`, `'[siteId+itemId], siteId'`… |
| `options.version` | Schema version, default `1`. Adding tables or indexes needs no bump. Changing an existing table's primary key cannot be migrated, with or without a bump: the database is recreated, and cached data and the outbox are lost. |

## Typing your own tables

Inferred tables are typed for you. For a table of your own, augment the global `NuxtAirplaneStores` interface so `db.<table>` is typed in handlers:

```ts [app/airplane/stores.ts]
declare global {
  interface NuxtAirplaneStores {
    drafts: { id?: number, siteId: string, body: string }
  }
}

export default defineAirplaneStores({
  Item: 'name',
  drafts: '++id, siteId',
})
```

`db.drafts` is then a `Table<{ id?: number, siteId: string, body: string }>`.

## Reserved names

`queries`, `mutations`, `meta`, `results` and `base` belong to the module.
