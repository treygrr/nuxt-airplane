`useMutation` takes the name of a mutation document and returns a `mutate` function.

```vue
<script setup lang="ts">
const rename = useMutation('RenameSite')

async function save(id: string, name: string) {
  await rename.mutate({ id, name })
}
</script>
```

## What `mutate` does

1. Adds a row to the outbox with the document name and the variables you passed.
2. Runs the mutation's [`apply` handler](/guide/mutation-handlers), if there is one, so the tables (and every `useAirplaneQuery` reading them) reflect the change immediately. The rows it touches are snapshotted so the change can be [rolled back](/guide/sync-and-offline#rolling-back).
3. Resolves with the outbox row.
4. Kicks the sync loop. If the app is online the mutation is sent right away; otherwise it waits.

Pass the handler's [local variables](/guide/mutation-handlers#local) in the same object. They reach the hooks and are kept on the outbox row, and only the mutation's own variables are sent.

`mutate` resolves as soon as the change is visible locally, not when the server has accepted it. That is the point: the UI never waits on the network.

When the server needs to answer before the UI can continue, pass `{ queue: false }`; see [Online-only mutations](#online-only-mutations).

## Return value

| Field | Type | |
| --- | --- | --- |
| `mutate` | `(variables) => Promise<MutationRow>` | Apply locally and queue. |
| `loading` | `Ref<boolean>` | `true` while `apply` runs. |
| `error` | `Ref<Error \| null>` | Error thrown by `apply`, if any. |

The resolved `MutationRow` has the queue `id`, which you can hand to `rollback(id)` from [`useSync()`](/guide/sync-and-offline).

## One press, one mutation

Every call to `mutate` queues a mutation, so two quick presses of a button queue two. For most changes that is only wasteful. For a delete it is an error: the first is sent, the thing is gone, and the second reaches the server after it and fails, so the user sees a change that did not save for something that did.

Bind the button to `loading`. It turns `true` as `mutate` is called, before the button can be pressed again, and back to `false` once `apply` has run. By then the row the button belongs to is usually gone from the page.

Disable the button as well as showing it busy. A UI library's loading state may only block the pointer: Vuetify's `v-btn` ignores clicks while `loading` through its stylesheet, but a focused button still answers Enter. `disabled` stops both.

```vue
<script setup lang="ts">
const remove = useMutation('DeleteWishlist')
</script>

<template>
  <v-btn
    :loading="remove.loading.value"
    :disabled="remove.loading.value"
    @click="remove.mutate({ id: list.id })"
  >
    Delete
  </v-btn>
</template>
```

`loading` is a ref inside the returned object, so the template needs `.value`; destructure it in the script (`const { mutate, loading } = useMutation(...)`) to use it bare.

There is one `loading` for each `useMutation`, not for each row. In a list where every row has its own delete button, every button shows busy while any of them is being applied, which is a few milliseconds. To mark only the row that was pressed, keep its id while you `await` the call:

```ts
const remove = useMutation('RemoveSiteItem')
const removing = ref<string | null>(null)

async function removeItem(item: { id: string, siteId: string, variantId: string }) {
  removing.value = item.id
  try {
    await remove.mutate({ siteId: item.siteId, variantId: item.variantId })
  }
  finally {
    removing.value = null
  }
}
```

This guards one button on one page. The same change can still be sent twice another way: from two tabs, or queued twice offline before either is sent. Write deletes on the server so that removing something already gone succeeds, and let [`merge`](/guide/mutation-handlers#merge) fold repeats that are still waiting in the queue.

## Server errors

If the server answers with GraphQL errors the mutation is marked `failed` and left in the queue, with the message in `error`. The user can `retry(id)` or `rollback(id)`. Only the mutations that [depend on it or must follow it](#chains) wait for that; the rest of the queue keeps syncing. A network failure is different: the batch stops and everything stays `pending` for the next attempt. So is an answer that is not about the mutation, such as an expired session: see [Sync and offline](/guide/sync-and-offline#the-sync-loop).

## Ordering

Mutations are queued, and applied locally, in the order `mutate` was called, one at a time. Two fired from one click handler without awaiting the first (add an item, then put it in a cart) land in that order.

The queue is sent oldest first, so dependent changes (create a site, then add an item to it) arrive in the order they were made. Mutations that have [nothing to do with each other](/guide/sync-and-offline#side-by-side) are sent side by side, and repeated edits of the same thing can be [merged into one](/guide/mutation-handlers#merge) before they are sent.

## Creating offline, then editing

A row created offline has no server id yet, but the user can still rename it, add items to it or delete it before the connection is back. Those later mutations reference an id the server has never seen.

The module handles this with placeholder ids. In the create's `apply` handler, mint the id with `tempId()`; in its `reconcile`, tell the module what the server replaced it with:

```ts [app/airplane/mutations/create-site.ts]
export default defineMutationHandler('CreateSite', {
  apply: ({ db, variables, tempId }) =>
    db.Site.put({ id: tempId(), name: variables.name, archived: false, items: [] }),
  reconcile: ({ tempIds, resolve }, result) => resolve(tempIds[0], result.createSite.id),
  refetch: ['GetSites'],
})
```

Nothing else changes. The component reads the new row from the live query, with its `tmp-…` id, and calls `rename.mutate({ id, name })` as usual. When the queue is sent:

1. `CreateSite` goes out. Its `reconcile` calls `resolve`, which re-keys the local row and rewrites every queued mutation that carries the placeholder, however deeply nested in its variables, to the real id. The server's version of the row moves with it, so a later re-apply or rollback finds the real row.
2. `RenameSite` reaches the server with the id it knows.

Placeholders are stable: if fresh server data arrives while the create is still queued, `apply` is re-run and `tempId()` hands out the same id, so the queued rename still points at the right row. Resolved ids are remembered (the last 1000) after the queue drains, so a component that still holds a placeholder it read earlier keeps working: a mutation queued with one is rewritten to the real id as it is queued.

If a mutation is about to be sent with a placeholder that was never resolved, because the create failed or its `reconcile` did not call `resolve`, it is marked `failed` with a message saying which id, instead of being sent and rejected by the server.

### A placeholder or a real id

Most code never needs to know which kind of id a row has. Where it does, ask `isTempId(id)`: it is `true` for an id `tempId()` minted that the server has not named yet, and `false` for anything else. It is auto-imported in components, composables and handler files, works during SSR, and can be imported from `#nuxt-airplane` too. Don't match the `tmp-` prefix by hand: the format is the module's own and may change.

A row created offline can be shown as not saved yet, and kept out of a link to a page that would only outlive its id:

```vue [app/components/SiteRow.vue]
<script setup lang="ts">
defineProps<{ site: { id: string, name: string } }>()
</script>

<template>
  <li>
    <span v-if="isTempId(site.id)">{{ site.name }} <em>not saved yet</em></span>
    <NuxtLink v-else :to="`/sites/${site.id}`">{{ site.name }}</NuxtLink>
  </li>
</template>
```

A `store` handler that replaces a whole table with a response needs no such check: it can clear the table and write what the server sent, and the rows queued mutations created are put back on top, the same as any other pending change (see [Two layers](/guide/stores-and-query-handlers#two-layers)).

::note
Coming from urql's graphcache offline exchange: this is the gap where an optimistic insert got a temporary id and a queued update on it failed on replay. Here the update is rewritten before it is sent.
::

## Chains

Two things link a mutation to one queued before it, and the outbox row records them in `dependsOn`:

- it carries, in its variables, a **placeholder** the earlier mutation minted;
- its `apply` touches something the earlier mutation **created** and the server has not seen yet: a row, or an element with an `id` in a list inside a row, such as an item added to a site.

Create a site offline, add a catalog item to it, set the item's quantity: the add carries the site's placeholder, the quantity update changes the item the add put on the site, and the three form a chain, whether or not the item has an id of its own. Nothing is declared.

The chain is the unit of failure:

- When the server rejects a mutation, the mutations below it in the chain wait, unsent, until it is retried or rolled back. The rest of the queue is not held up: a rename of another site queued after the failed create goes out in the same batch. `useSync().blocked` counts the waiting mutations.
- Retrying the failed mutation sends it and then its chain, in order, each with the ids the one before it resolved.
- Rolling it back drops the mutations below it that have nothing left to do: those that carry its placeholder, and those whose `apply` now changes nothing. One that still does something on its own, such as a corrected save of the same new row, stays queued.

### Edits of the same thing

Two queued mutations that wrote the same piece of the same thing are ordered as well: two renames of one site, two quantities for one item. The later one is recorded as coming `after` the earlier one and waits while that one is failed, so the server never applies them the wrong way round. This is order only. Rolling the earlier one back leaves the later one queued, and it goes out.

A piece is a field, or an element in a list. A rename and an archive of the same site write different fields and stay independent, and so do two items added to the same site.

What does not link:

- A placeholder the server has already named. By the time the mutation is sent it is a real id.
- Two mutations on the same existing row that write different fields, a rename and then an archive. A rejected rename does not hold the archive back.
- A single nested object with an `id`, such as an owner or a category. It refers to something that exists elsewhere, so assigning one twice is two independent mutations. Only list elements are things a mutation creates.
- Removing what holds a created thing. Deleting a site does not depend on the items added to it; removing one of those items does.

## Online-only mutations

Some mutations cannot wait in a queue: a checkout, a payment, a form whose response the UI needs right away. Pass `{ queue: false }` and `mutate` sends the request now and resolves with the server's data:

```vue
<script setup lang="ts">
const checkout = useMutation('Checkout', { queue: false })

async function pay() {
  const { checkout: order } = await checkout.mutate({ cartId })
  await navigateTo(`/orders/${order.id}`)
}
</script>
```

With `queue: false`:

- Nothing is written to the outbox and no `apply` handler runs. `loading` is `true` while the request is in flight.
- The outbox is drained first, so the server sees every change queued before it (the cart the checkout is for).
- Placeholder ids in the variables are replaced the same way as for queued mutations.
- The handler's `reconcile` runs with the response, and the queries in its `refetch` list are refetched, or every mounted query when it has none.
- It rejects while offline, and on GraphQL errors, with the error message. Nothing is retried.

The same call is available as `execute(name, variables)` on the client from [`useAirplane()`](/api/use-airplane).
