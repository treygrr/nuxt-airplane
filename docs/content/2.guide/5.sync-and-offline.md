`useSync()` exposes the state of the mutation queue and the controls around it.

```vue
<script setup lang="ts">
const {
  online, syncing, synced, pending, syncTotal, syncCount, lastError,
  sync, rollback, retry, goOffline, goOnline
} = useSync()
</script>

<template>
  <header>
    <strong>{{ online ? 'Online' : 'Offline' }}</strong>
    <span v-if="syncing">Syncing {{ syncCount }} / {{ syncTotal }}…</span>
    <span v-else-if="synced">Synced</span>
    <span v-else>{{ pending.length }} pending</span>
  </header>
</template>
```

## The sync loop

The queue is sent whenever:

- a mutation is queued while online,
- the browser fires `online`,
- `goOnline()` is called,
- `sync()` is called,
- the app starts (to drain anything left from a previous session).

A trigger that arrives while a batch is being sent does not join that batch but starts another run as soon as it ends, so a mutation queued mid-batch goes out right after it. `sync()` resolves once the queue is drained or blocked.

Mutations go out oldest first, one at a time. For each one the loop replaces any [placeholder id](/guide/mutations#creating-offline-then-editing) in the variables with the server id it was resolved to, sends the request, runs the [`reconcile` handler](/guide/mutation-handlers#reconcile), removes it from the queue and bumps `syncCount`. After the batch, the queries named in the handlers' `refetch` lists are refetched (or every mounted query if a handler has no list).

A network error stops a batch; a rejected mutation holds back only its chain:

- **A network error** sets `lastError`, leaves the mutation `pending` and stops. The next trigger resumes from there.
- **An answer about the session or the server**, not about the mutation, is treated the same way: an expired token or a busy server would reject everything queued behind it too. By default that is HTTP 401, 429 and 5xx, and the error codes `UNAUTHENTICATED`, `TOO_MANY_REQUESTS` and `RATE_LIMITED`; [`retryLater`](/guide/auth-and-headers#errors-that-are-not-about-the-mutation) changes the rule.
- **GraphQL errors**, or a placeholder id that was never resolved, mark that mutation `failed` with the message. The batch goes on, except for the mutations that [depend on it](/guide/mutations#chains): an item added to a site whose creation failed would fail too, so it waits, unsent, until the create is retried or rolled back. So does a later edit of the same field, which must not overtake it. `blocked` counts the waiting mutations. Everything else keeps syncing.

## Multiple tabs

Every tab of the app shares the same database, so a change made in one tab shows up in the others through the live queries. The outbox is shared too, which is why only one tab drains it at a time: the sync loop takes a [Web Lock](https://developer.mozilla.org/docs/Web/API/Web_Locks_API) named after the database before sending. A tab that finds the lock taken waits its turn and then sends whatever is still queued, usually nothing. If the tab holding the lock is closed mid-batch, the browser releases the lock and the next tab picks up where it left off, re-queuing the row that was in flight.

`syncing` is `true` only in the tab doing the sending. Browsers without the Web Locks API (and insecure contexts, where it is unavailable) fall back to each tab syncing on its own.

## Pending changes

`pending` is a live list of the outbox rows, oldest first. Each row has `id`, `document`, `variables`, a human-readable `description` (from the handler's [`describe`](/guide/mutation-handlers#describe) hook, or the humanized document name), `status` (`pending` · `syncing` · `failed`), `createdAt`, `dependsOn` and `after` (the ids of the queued mutations it [depends on or must follow](/guide/mutations#chains)) and, for failed rows, `error`. Showing it to users lets them see what hasn't reached the server and act on it.

A pending row whose chain holds a failed mutation is waiting on it. `blocked` counts them; to mark them in the list, walk the chain the way the module does:

```ts
const held = computed(() => {
  const ids = new Set(pending.value.filter(m => m.status === 'failed').map(m => m.id))
  for (const m of pending.value) if ([...(m.dependsOn ?? []), ...(m.after ?? [])].some(id => ids.has(id))) ids.add(m.id)
  return ids
})
```

## Rolling back

`rollback(id)` undoes a queued mutation and removes it from the queue, together with the mutations that [depend on it](/guide/mutations#chains) and have nothing left to do without it. Roll back the creation of a site and the items added to it offline go with it; roll back one of those items and the site stays.

Everything queued after the rolled-back mutation is unwound from the undo logs, newest first, then `apply` is re-run for each on the restored data, so later changes survive and stay undoable themselves. A dependent is dropped when it carries a placeholder that will now never resolve, or when applying it again changes nothing, such as a quantity set on an item that is gone. One that still does something stays queued on its own: a corrected save of the same new row, for example. A mutation with a `revert` handler is undone through it instead of its log.

`rollback` resolves with the mutations it dropped, and `dependents(id)` lists the ones that depend on it, so the UI can say so first:

```vue
<button @click="rollback(m.id)">
  Roll back<template v-if="dependents(m.id).length"> and {{ dependents(m.id).length }} more</template>
</button>
```

Say a user, offline, changes a quantity and then removes an item. Rolling back the quantity change puts the old quantity back while the removal stays applied.

A mutation that is being sent right now (`syncing`) cannot be rolled back.

## Retrying

`retry(id)` puts a `failed` mutation back to `pending` and syncs; the mutations waiting on it go out right after it, in order. Rolling a failed mutation back drops the ones that cannot go on without it and releases the rest.

## Going offline on purpose

`goOffline()` holds the client offline whatever the network says: queries are read from the tables only and mutations stay queued. `goOnline()` releases the hold and syncs. Use it for a "work offline" switch, or to test offline behaviour without touching devtools.

`online` is the effective state. `networkOnline` (what the browser reports) and `forcedOffline` (whether `goOffline()` is in effect) expose the two inputs.

## Reference

| Field | Type | |
| --- | --- | --- |
| `online` | `Ref<boolean>` | `networkOnline && !forcedOffline` |
| `networkOnline` | `Ref<boolean>` | What `navigator.onLine` reports. |
| `forcedOffline` | `Ref<boolean>` | `true` while held by `goOffline()`. |
| `syncing` | `Ref<boolean>` | A batch is being sent. |
| `synced` | `Ref<boolean>` | Nothing queued and nothing in flight. |
| `pending` | `Ref<MutationRow[]>` | Queued mutations, oldest first. |
| `blocked` | `Ref<number>` | Pending mutations waiting on a failed one they depend on. |
| `syncTotal` | `Ref<number>` | Size of the current (or last) batch. |
| `syncCount` | `Ref<number>` | Mutations of that batch sent so far. |
| `lastError` | `Ref<string \| null>` | Network error that stopped the last batch. |
| `prefetching` | `Ref<number>` | Paginated queries being fetched to the end for offline use. |
| `sync()` | `() => Promise<void>` | Send the queue now. |
| `rollback(id)` | `(id: number) => Promise<MutationRow[]>` | Undo and drop a queued mutation and the ones that depend on it. Resolves with them. |
| `dependents(id)` | `(id: number) => MutationRow[]` | The queued mutations that depend on one, directly or not: what rolling it back may drop. |
| `retry(id)` | `(id: number) => Promise<void>` | Re-queue a failed mutation and sync. |
| `goOffline()` | `() => void` | Hold the client offline. |
| `goOnline()` | `() => void` | Release the hold and sync. |
