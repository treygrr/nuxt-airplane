`useSync()` exposes the state of the mutation queue and the controls around it.

```vue
<script setup lang="ts">
const {
  online, syncing, synced, pending, syncTotal, syncCount, lastError,
  sync, rollback, retry, goOffline, goOnline
} = useSync()
</script>

<template>
  <header>
    <strong>{{ online ? 'Online' : 'Offline' }}</strong>
    <span v-if="syncing">Syncing {{ syncCount }} / {{ syncTotal }}…</span>
    <span v-else-if="synced">Synced</span>
    <span v-else>{{ pending.length }} pending</span>
  </header>
</template>
```

## The sync loop

The queue is sent whenever:

- a mutation is queued while online,
- the browser fires `online`,
- `goOnline()` is called,
- `sync()` is called,
- the app starts (to drain anything left from a previous session).

A trigger that arrives while a batch is being sent does not join that batch but starts another run as soon as it ends, so a mutation queued mid-batch goes out right after it. `sync()` resolves once the queue is drained or blocked.

Mutations go out oldest first, one at a time. For each one the loop replaces any [placeholder id](/guide/mutations#creating-offline-then-editing) in the variables with the server id it was resolved to, sends the request, runs the [`reconcile` handler](/guide/mutation-handlers#reconcile), removes it from the queue and bumps `syncCount`. After the batch, the queries named in the handlers' `refetch` lists are refetched (or every mounted query if a handler has no list).

Two things stop a batch early:

- **A network error** sets `lastError`, leaves the mutation `pending` and stops. The next trigger resumes from there.
- **GraphQL errors**, or a placeholder id that was never resolved, mark that mutation `failed` with the message and, by default, stop the batch: everything queued after it is held back until it is retried or rolled back, because it may depend on it (an item added to a site whose creation failed would fail too). `blocked` counts the held-back mutations. Set the [`stopOnFailure`](/getting-started/configuration#stoponfailure) option to `false` to skip failed mutations and keep sending the rest, if yours are independent.

## Multiple tabs

Every tab of the app shares the same database, so a change made in one tab shows up in the others through the live queries. The outbox is shared too, which is why only one tab drains it at a time: the sync loop takes a [Web Lock](https://developer.mozilla.org/docs/Web/API/Web_Locks_API) named after the database before sending. A tab that finds the lock taken waits its turn and then sends whatever is still queued, usually nothing. If the tab holding the lock is closed mid-batch, the browser releases the lock and the next tab picks up where it left off, re-queuing the row that was in flight.

`syncing` is `true` only in the tab doing the sending. Browsers without the Web Locks API (and insecure contexts, where it is unavailable) fall back to each tab syncing on its own.

## Pending changes

`pending` is a live list of the outbox rows, oldest first. Each row has `id`, `document`, `variables`, a human-readable `description` (from the handler's [`describe`](/guide/mutation-handlers#describe) hook, or the humanized document name), `status` (`pending` · `syncing` · `failed`), `createdAt` and, for failed rows, `error`. Showing it to users lets them see what hasn't reached the server and act on it.

## Rolling back

`rollback(id)` undoes a queued mutation and removes it from the queue. With no `revert` handler the module replays the writes recorded while that mutation's `apply` ran — whether to the cached responses or to your own tables — backwards, then re-runs `apply` for every mutation queued after it, so later changes survive.

Say a user, offline, changes a quantity and then removes an item. Rolling back the quantity change puts the old quantity back while the removal stays applied.

A mutation that is being sent right now (`syncing`) cannot be rolled back.

## Retrying

`retry(id)` puts a `failed` mutation back to `pending` and syncs; the mutations held back behind it go out right after it. Rolling a failed mutation back releases them too.

## Going offline on purpose

`goOffline()` holds the client offline whatever the network says: queries serve the cache only and mutations stay queued. `goOnline()` releases the hold and syncs. Use it for a "work offline" switch, or to test offline behaviour without touching devtools.

`online` is the effective state. `networkOnline` (what the browser reports) and `forcedOffline` (whether `goOffline()` is in effect) expose the two inputs.

## Reference

| Field | Type | |
| --- | --- | --- |
| `online` | `Ref<boolean>` | `networkOnline && !forcedOffline` |
| `networkOnline` | `Ref<boolean>` | What `navigator.onLine` reports. |
| `forcedOffline` | `Ref<boolean>` | `true` while held by `goOffline()`. |
| `syncing` | `Ref<boolean>` | A batch is being sent. |
| `synced` | `Ref<boolean>` | Nothing queued and nothing in flight. |
| `pending` | `Ref<MutationRow[]>` | Queued mutations, oldest first. |
| `blocked` | `Ref<number>` | Pending mutations held back behind a failed one (`stopOnFailure`). |
| `syncTotal` | `Ref<number>` | Size of the current (or last) batch. |
| `syncCount` | `Ref<number>` | Mutations of that batch sent so far. |
| `lastError` | `Ref<string \| null>` | Network error that stopped the last batch. |
| `prefetching` | `Ref<number>` | Paginated queries being fetched to the end for offline use. |
| `sync()` | `() => Promise<void>` | Send the queue now. |
| `rollback(id)` | `(id: number) => Promise<void>` | Undo and drop a queued mutation. |
| `retry(id)` | `(id: number) => Promise<void>` | Re-queue a failed mutation and sync. |
| `goOffline()` | `() => void` | Hold the client offline. |
| `goOnline()` | `() => void` | Release the hold and sync. |
