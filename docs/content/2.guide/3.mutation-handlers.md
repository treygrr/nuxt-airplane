A mutation handler tells the module what a mutation means for the local data: which rows change in the tables your [query handlers](/guide/stores-and-query-handlers) read from. Without one the mutation still queues and syncs, but the UI only catches up after the next refetch.

Handlers live in files under `app/airplane/` (configurable with [`handlersDir`](/getting-started/configuration#handlersdir)). Each file default-exports a `defineMutationHandlers()` map; all files are merged.

```ts [app/airplane/sites.ts]
export default defineMutationHandlers({
  ArchiveSite: {
    apply: ({ db, variables }) => db.Site.update(variables.id, { archived: true }),
    refetch: ['GetSites']
  }
})
```

Keys are mutation document names, so they are type-checked, and `variables` inside each handler is typed from that mutation. `db.Site` is typed too: the table was [inferred from the documents](/guide/stores-and-query-handlers#inferred-tables).

## Hooks

### `describe`

A human-readable summary for the pending list: a string, or a function of the handler context returning one. It runs once, when the mutation is queued and **before** `apply`, so it can still read the data as it was — the old name in a rename, the site about to be deleted. The result is stored on the outbox row as `description` and never recomputed, so it stays meaningful offline even if what it referred to changes later.

```ts
RenameSite: {
  describe: async ({ db, variables }) =>
    `Rename ${(await db.Site.get(variables.id))?.name ?? variables.id} to ${variables.name}`,
  apply: ({ db, variables }) => db.Site.update(variables.id, { name: variables.name })
}
```

Without `describe`, the document name is humanized: `ArchiveSite` becomes "Archive site".

### `apply`

Runs when the mutation is queued. Edit the tables so the change shows up immediately: every query whose `read` touches the rows re-renders.

`apply` runs inside a Dexie read-write transaction over every table, and each write it makes is recorded for rollback. If it throws, the transaction aborts (nothing is kept) and `mutate()` rejects without queuing anything.

It runs again whenever the data under the queue changes: a response is stored, or a mutation queued before it is rolled back. If it throws then, what it wrote is taken back and the mutation stays queued: it is still sent, but its change is not shown until it syncs, and a console warning names it.

::warning
Because it runs in a transaction, `apply` should only await Dexie operations. Awaiting a `fetch` or a timer commits the transaction early and later writes fail.
::

### `reconcile`

Runs with the server's response once the mutation has been sent. Use it to merge server-assigned values (ids, timestamps) into the local data.

```ts
CreateSite: {
  apply: ({ db, variables, tempId }) =>
    db.Site.put({ id: tempId(), name: variables.name, archived: false, items: [] }),
  reconcile: ({ tempIds, resolve }, result) => resolve(tempIds[0], result.createSite.id)
}
```

`tempId()` mints a placeholder id for the row the server will create, and `resolve()` tells the module which real id it got. `resolve` also re-keys the row, in whichever table holds it under the placeholder, [inferred](/guide/stores-and-query-handlers#inferred-tables) or your own. A copy nested in another row (an item on a site), or a reference to it there, is left to the refetch that follows. That is what lets the user keep working on the new row while offline: see [Creating offline, then editing](/guide/mutations#creating-offline-then-editing).

Anything else `reconcile` writes lands on top of the queue, not under it. If another queued mutation on the same row is rolled back or rebased later, that value can be lost locally until a response carries the row again, so keep `reconcile` to ids and to values the refetch brings anyway.

`reconcile` also runs for mutations sent with [`queue: false`](/guide/mutations#online-only-mutations); `tempIds` is empty then, since nothing was applied locally.

### `revert`

Runs when the user rolls the mutation back, instead of the automatic undo. Provide it only when undoing the recorded writes isn't the right thing — for example when `apply` also had side effects outside the database.

### `refetch`

Query names to refetch after the server accepted the mutation. When omitted every mounted query is refetched.

## The handler context

Every hook receives `{ db, variables }`. `apply` also gets `tempId`, and `reconcile` gets `tempIds` and `resolve`.

### `db`

The Dexie instance: one table per type your documents select with an id, any you declared with [`defineAirplaneStores`](/guide/stores-and-query-handlers), and the module's `queries`, `mutations` and `meta` tables. Every table is typed through the global `NuxtAirplaneStores` interface.

### `variables`

The variables the mutation was queued with, typed from the mutation document. In `reconcile` they are the variables as sent, with any temp id already replaced by its server id.

### `tempId()` (apply only)

Returns a placeholder id (`tmp-` plus a UUID) for a row the server will assign an id to. Call it once per row you create. The ids are stored on the outbox row, so when `apply` is re-run on fresh server data (a [rebase](/guide/stores-and-query-handlers#rebase-on-refetch)) the same ids come back in the same order and the local rows keep their identity. A mutation queued later with one of them in its variables depends on this one: see [Chains](/guide/mutations#chains).

### `tempIds` and `resolve()` (reconcile only)

`tempIds` lists the ids `apply` minted, in call order. `resolve(tempId, id)` records that the placeholder now stands for the server's `id`: the row under the placeholder is re-keyed, in whichever table holds it, and every queued mutation that carries the placeholder is rewritten to the real id, in its variables and in its undo log. Forgetting to call it fails those mutations with a message that says so, instead of sending the placeholder to the server.

## Organizing handler files

Everything under `app/airplane/` is scanned, at any depth, and every default export created with a `define*` helper is registered: handlers, stores and [`defineAirplaneRequest`](/guide/auth-and-headers). Two layouts work well:

**One file per operation**, with the singular helpers. No index needed; each file is picked up on its own.

```
app/airplane/
  stores.ts
  mutations/
    archive-site.ts      → export default defineMutationHandler('ArchiveSite', { … })
    rename-site.ts
```

**One file per operation, composed in an index.** A folder with an `index.ts` is treated as a unit: only the index is imported, so the pieces don't register twice.

```
app/airplane/
  queries/
    get-sites.ts         → export default defineQueryHandler('GetSites', { … })
    get-items.ts
    index.ts             → export default defineQueryHandlers({ ...getSites, ...getItems })
```

Shared lookups belong in `app/utils/`, which Nuxt auto-imports; types such as `AirplaneDexie` come from `#nuxt-airplane`.

Every default export in the directory must be the result of a `define*` helper. One that visibly isn't (an object or array literal, a function, a call to something else) **fails the build** with the file name, so a forgotten wrapper can't silently drop a handler. A default export the build can't see through (an identifier, `export default handlers`) is checked at runtime instead and ignored with a console warning if it isn't tagged.

## How rollback works

While `apply` runs, a Dexie middleware records every write — `put`, `add`, `update`, `delete`, on any table except the outbox — together with the row as it was before. The log is stored on the queued mutation.

`rollback(id)` unwinds the logs of every mutation queued after it, newest first, then its own; drops it together with the mutations that [depend on it](/guide/mutations#chains); and re-runs `apply` for the survivors, so their changes land on the restored data with fresh logs. It covers every table, which is why most handlers never need `revert`.

## Reading other data

A handler can read anything in the database. The playground's `AddSiteItem` looks up the item's name in the `Item` table, filled by the catalog queries, so the new entry renders with a name before the server has seen it:

```ts
AddSiteItem: {
  async apply({ db, variables }) {
    const name = (await db.Item.get(variables.itemId))?.name ?? variables.itemId
    await db.Site.update(variables.siteId, (site) => {
      site.items = [...site.items, { id: variables.itemId, name, onHand: variables.onHand ?? 0 }]
    })
  }
}
```
