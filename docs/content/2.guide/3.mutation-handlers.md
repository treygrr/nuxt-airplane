A mutation handler tells the module what a mutation means for the local data. Without one the mutation still queues and syncs, but the UI only catches up after the next refetch.

Handlers live in files under `app/airplane/` (configurable with [`handlersDir`](/getting-started/configuration#handlersdir)). Each file default-exports a `defineMutationHandlers()` map; all files are merged.

```ts [app/airplane/sites.ts]
export default defineMutationHandlers({
  ArchiveSite: {
    apply: ({ cache, variables }) =>
      cache.update('GetSites', (data) => {
        const site = data.sites.find(s => s.id === variables.id)
        if (site) site.archived = true
      }),
    refetch: ['GetSites']
  }
})
```

Keys are mutation document names, so they are type-checked, and `variables` inside each handler is typed from that mutation.

When the query lives in [your own tables](/guide/stores-and-query-handlers) the handler writes to them instead:

```ts
ArchiveSite: {
  apply: ({ db, variables }) => db.Site.update(variables.id, { archived: true })
}
```

## Hooks

### `describe`

A human-readable summary for the pending list: a string, or a function of the handler context returning one. It runs once, when the mutation is queued and **before** `apply`, so it can still read the data as it was — the old name in a rename, the site about to be deleted. The result is stored on the outbox row as `description` and never recomputed, so it stays meaningful offline even if what it referred to changes later.

```ts
RenameSite: {
  describe: async ({ db, variables }) =>
    `Rename ${(await db.Site.get(variables.id))?.name ?? variables.id} to ${variables.name}`,
  apply: ({ db, variables }) => db.sites.update(variables.id, { name: variables.name })
}
```

Without `describe`, the document name is humanized: `ArchiveSite` becomes "Archive site".

### `apply`

Runs when the mutation is queued. Edit the local data so the change shows up immediately.

`apply` runs inside a Dexie read-write transaction over every table, and each write it makes is recorded for rollback. If it throws, the transaction aborts (nothing is kept) and `mutate()` rejects without queuing anything.

::warning
Because it runs in a transaction, `apply` should only await Dexie operations. Awaiting a `fetch` or a timer commits the transaction early and later writes fail.
::

### `reconcile`

Runs with the server's response once the mutation has been sent. Use it to merge server-assigned values (ids, timestamps) into the local data.

```ts
CreateSite: {
  apply: ({ db, variables, tempId }) =>
    db.Site.put({ __typename: 'Site', id: tempId(), name: variables.name, archived: false, items: [] }),
  reconcile: ({ tempIds, resolve }, result) => resolve(tempIds[0], result.createSite.id)
}
```

`tempId()` mints a placeholder id for the row the server will create, and `resolve()` tells the module which real id it got. In an [inferred table](/guide/stores-and-query-handlers#inferred-tables) `resolve` also re-keys the row and repoints every stored reference to it; for a table of your own, move the row yourself before calling it. That is what lets the user keep working on the new row while offline: see [Creating offline, then editing](/guide/mutations#creating-offline-then-editing).

`reconcile` also runs for mutations sent with [`queue: false`](/guide/mutations#online-only-mutations); `tempIds` is empty then, since nothing was applied locally.

### `revert`

Runs when the user rolls the mutation back, instead of the automatic undo. Provide it only when undoing the recorded writes isn't the right thing — for example when `apply` also had side effects outside the database.

### `refetch`

Query names to refetch after the server accepted the mutation. When omitted every mounted query is refetched.

## The handler context

Every hook receives `{ db, cache, variables }`. `apply` also gets `tempId`, and `reconcile` gets `tempIds` and `resolve`.

### `db`

The Dexie instance: the module's `queries` and `mutations` tables plus any you declared with [`defineAirplaneStores`](/guide/stores-and-query-handlers), typed through the global `NuxtAirplaneStores` interface.

### `cache`

Helpers over the cached-blob responses of queries without a `read` handler.

| Method | |
| --- | --- |
| `update(name, updater)` | Run `updater(data, variables)` on every cached response of that query. Mutate `data` in place or return a replacement. |
| `update(name, variables, updater)` | Same, for one exact set of variables. |
| `get(name, variables?)` | Read a query's current data (through `read` when the query has one). |
| `set(name, variables, data)` | Write a cached response. |
| `invalidate(name)` | Drop the cached responses of a query; it is refetched once `apply` finishes. |

`name` is a query document name, so `data` inside the updater is typed as that query's result.

### `variables`

The variables the mutation was queued with, typed from the mutation document. In `reconcile` they are the variables as sent, with any temp id already replaced by its server id.

### `tempId()` (apply only)

Returns a placeholder id (`tmp-` plus a UUID) for a row the server will assign an id to. Call it once per row you create. The ids are stored on the outbox row, so when `apply` is re-run on fresh server data (a [rebase](/guide/stores-and-query-handlers#rebase-on-refetch)) the same ids come back in the same order and the local rows keep their identity.

### `tempIds` and `resolve()` (reconcile only)

`tempIds` lists the ids `apply` minted, in call order. `resolve(tempId, id)` records that the placeholder now stands for the server's `id`: every queued mutation whose variables mention the placeholder is rewritten before it is sent, a row under the placeholder in an inferred table is re-keyed, and references to it in stored queries are updated. Forgetting to call it fails those mutations with a message that says so, instead of sending the placeholder to the server.

## Organizing handler files

Everything under `app/airplane/` is scanned, at any depth, and every default export created with a `define*` helper is registered: handlers, stores and [`defineAirplaneRequest`](/guide/auth-and-headers). Two layouts work well:

**One file per operation**, with the singular helpers. No index needed; each file is picked up on its own.

```
app/airplane/
  stores.ts
  mutations/
    archive-site.ts      → export default defineMutationHandler('ArchiveSite', { … })
    rename-site.ts
```

**One file per operation, composed in an index.** A folder with an `index.ts` is treated as a unit: only the index is imported, so the pieces don't register twice.

```
app/airplane/
  queries/
    get-sites.ts         → export default defineQueryHandler('GetSites', { … })
    get-items.ts
    index.ts             → export default defineQueryHandlers({ ...getSites, ...getItems })
```

Shared lookups belong in `app/utils/`, which Nuxt auto-imports; types such as `AirplaneDexie` come from `#nuxt-airplane`.

Every default export in the directory must be the result of a `define*` helper. One that visibly isn't (an object or array literal, a function, a call to something else) **fails the build** with the file name, so a forgotten wrapper can't silently drop a handler. A default export the build can't see through (an identifier, `export default handlers`) is checked at runtime instead and ignored with a console warning if it isn't tagged.

## How rollback works

While `apply` runs, a Dexie middleware records every write — `put`, `add`, `update`, `delete`, on any table except the outbox — together with the row as it was before. The log is stored on the queued mutation.

`rollback(id)` replays that log backwards, then re-runs `apply` for every mutation queued after it so their changes land on the restored data. It works the same for `cache.update()` and for direct table writes, which is why most handlers never need `revert`.

## Reading other data

A handler can read anything in the database. The playground's blob-mode `AddSiteItem` looked up the item's name in the cached items catalog so the new row rendered with a name before the server had seen it:

```ts
AddSiteItem: {
  async apply({ cache, variables }) {
    const items = await cache.get('GetItems')
    const name = items?.items.find(i => i.id === variables.itemId)?.name ?? variables.itemId
    await cache.update('GetSites', (data) => {
      const site = data.sites.find(s => s.id === variables.siteId)
      site?.items.push({ id: variables.itemId, name, onHand: variables.onHand ?? 0 })
    })
  }
}
```
