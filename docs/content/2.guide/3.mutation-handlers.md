A mutation handler tells the module what a mutation means for the cached data. Without one the mutation still queues and syncs, but the UI only catches up after the next refetch.

Handlers live in files under `app/offline/` (configurable with [`handlersDir`](/getting-started/configuration#handlersdir)). Each file default-exports a `defineMutationHandlers()` map; all files are merged.

```ts [app/offline/sites.ts]
export default defineMutationHandlers({
  ArchiveSite: {
    apply: ({ cache, variables }) =>
      cache.update('GetSites', (data) => {
        const site = data.sites.find(s => s.id === variables.id)
        if (site) site.archived = true
      }),
    refetch: ['GetSites']
  }
})
```

Keys are mutation document names, so they are type-checked, and `variables` inside each handler is typed from that mutation.

## Hooks

### `apply`

Runs when the mutation is queued. Edit the cache so the change shows up immediately. The rows it touches are recorded before the first write, which is what makes rollback possible.

If `apply` throws, the touched rows are restored and `mutate()` rejects; nothing is queued.

### `reconcile`

Runs with the server's response once the mutation has been sent. Use it to merge server-assigned values (ids, timestamps) into the cache.

```ts
CreateSite: {
  apply: ({ cache, variables }) =>
    cache.update('GetSites', (data) => {
      data.sites.push({ id: `tmp-${Date.now()}`, name: variables.name, archived: false })
    }),
  reconcile: ({ cache, variables }, result) =>
    cache.update('GetSites', (data) => {
      const site = data.sites.find(s => s.name === variables.name && s.id.startsWith('tmp-'))
      if (site) site.id = result.createSite.id
    })
}
```

### `revert`

Runs when the user rolls the mutation back. When omitted the module restores the rows `apply` touched from its snapshot, then replays the `apply` of every later pending mutation. Provide `revert` when a snapshot isn't the right undo — for instance when the change also touched your own Dexie tables.

### `refetch`

Query names to refetch after the server accepted the mutation. When omitted every mounted query is refetched.

## The handler context

Every hook receives `{ db, cache, variables }`.

### `cache`

| Method | |
| --- | --- |
| `update(name, updater)` | Run `updater(data, variables)` on every cached response of that query. Mutate `data` in place or return a replacement. |
| `update(name, variables, updater)` | Same, for one exact set of variables. |
| `get(name, variables?)` | Read a cached response. |
| `set(name, variables, data)` | Write a cached response. |
| `invalidate(name)` | Drop the cached responses of a query and refetch any mounted instance. |

`name` is a query document name, so `data` inside the updater is typed as that query's result.

### `variables`

The variables the mutation was queued with, typed from the mutation document.

### `db`

The Dexie instance, with the module's `queries` and `mutations` tables, if you need to go lower than the cache helpers.

## Reading other queries

A handler can read any cached query. The playground's `AddSiteItem` looks up the item's name in the items catalog so the new row renders with a name before the server has seen it:

```ts
AddSiteItem: {
  async apply({ cache, variables }) {
    const items = await cache.get('GetItems')
    const name = items?.items.find(i => i.id === variables.itemId)?.name ?? variables.itemId
    await cache.update('GetSites', (data) => {
      const site = data.sites.find(s => s.id === variables.siteId)
      site?.items.push({ id: variables.itemId, name, onHand: variables.onHand ?? 0 })
    })
  }
}
```
