A mutation handler tells the module what a mutation means for the local data: which rows change in the tables your [query handlers](/guide/stores-and-query-handlers) read from. Without one the mutation still queues and syncs, but the UI only catches up after the next refetch.

Handlers live in files under `app/airplane/` (configurable with [`handlers.dir`](/getting-started/configuration#handlersdir)). Each file default-exports a `defineMutationHandlers()` map; all files are merged.

```ts [app/airplane/sites.ts]
export default defineMutationHandlers({
  ArchiveSite: {
    apply: ({ db, variables }) => db.Site.update(variables.id, { archived: true }),
    refetch: ['GetSites']
  }
})
```

Keys are mutation document names, so they are type-checked, and `variables` inside each handler is typed from that mutation. `db.Site` is typed too: the table was [inferred from the documents](/guide/stores-and-query-handlers#inferred-tables).

## Hooks

### `describe`

A human-readable summary for the pending list: a string, or a function of the handler context returning one. It runs once, when the mutation is queued and **before** `apply`, so it can still read the data as it was — the old name in a rename, the site about to be deleted. The result is stored on the outbox row as `description` and never recomputed, so it stays meaningful offline even if what it referred to changes later.

```ts
RenameSite: {
  describe: async ({ db, variables }) =>
    `Rename ${(await db.Site.get(variables.id))?.name ?? variables.id} to ${variables.name}`,
  apply: ({ db, variables }) => db.Site.update(variables.id, { name: variables.name })
}
```

Without `describe`, the document name is humanized: `ArchiveSite` becomes "Archive site".

### `apply`

Runs when the mutation is queued. Edit the tables so the change shows up immediately: every query whose `read` touches the rows re-renders.

`apply` runs inside a Dexie read-write transaction over every table. If it throws, the transaction aborts (nothing is kept) and `mutate()` rejects without queuing anything. The module notes which rows it changed and keeps the server's version of each, which is all a rollback needs, and what it created, a row or an element with an `id` in a list inside one, so that a later mutation touching it [depends on this one](/guide/mutations#chains).

It runs again whenever the queue is put back on the tables: a response carried a row the queue had changed, or a mutation on the same rows was rolled back or accepted. If it throws then, what it wrote is taken back and the mutation stays queued: it is still sent, but its change is not shown until it syncs, and a console warning names it.

::warning
Because it runs in a transaction, `apply` should only await Dexie operations. Awaiting a `fetch` or a timer commits the transaction early and later writes fail.
::

### `reconcile`

Runs with the server's response once the mutation has been sent. Use it to merge server-assigned values (ids, timestamps) into the local data.

```ts
CreateSite: {
  apply: ({ db, variables, tempId }) =>
    db.Site.put({ id: tempId(), name: variables.name, archived: false, items: [] }),
  reconcile: ({ tempIds, resolve }, result) => resolve(tempIds[0], result.createSite.id)
}
```

`tempId()` mints a placeholder id for the row the server will create, and `resolve()` tells the module which real id it got. `resolve` also re-keys the row, in whichever table holds it under the placeholder, [inferred](/guide/stores-and-query-handlers#inferred-tables) or your own. A copy nested in another row (an item on a site), or a reference to it there, is left to the refetch that follows. That is what lets the user keep working on the new row while offline: see [Creating offline, then editing](/guide/mutations#creating-offline-then-editing).

Anything else `reconcile` writes is treated as server data: where a queued mutation has changed the same row, the write is carried into the server's version of it, so it is still there after a rollback.

`reconcile` also runs for mutations sent with [`queue: false`](/guide/mutations#online-only-mutations); `tempIds` is empty then, since nothing was applied locally.

### `revert`

Runs when the user rolls the mutation back, before the rows go back to the server's version. The tables need nothing from it: provide it only when `apply` also had side effects outside the database.

### `merge`

Folds a mutation queued later into one of the same document that is still waiting. A cart line whose quantity is tapped from 1 to 5 queues five mutations; with `merge` the server gets one.

```ts
export default defineMutationHandler('SetCartLineQuantity', {
  apply: ({ db, variables }) => db.CartLine.update(variables.lineId, { quantity: variables.quantity }),
  // Same line: the later quantity is the only one that matters.
  merge: (earlier, later) => earlier.lineId === later.lineId && later,
})
```

It receives the variables of both and returns those of the one mutation that stands for them, or nothing when they are not about the same thing. For a mutation that sets a value, that is the later variables. For one that adds to a value, add the two up. Keep it pure: it reads nothing but its arguments.

The module only merges where that cannot change the outcome:

- into a mutation that has **never been sent**. One that went out and came back with a network error may have reached the server, which would take a changed version of it for a retry;
- when **nothing queued in between** changed the same rows or is linked to the new mutation;
- when the new mutation **minted no placeholder id**.

`mutate` then resolves with the row the mutation was merged into, which takes the merged variables and a fresh `describe`. Rolling it back undoes both edits.

### `refetch`

Query names to refetch after the server accepted the mutation. When omitted, the module refetches the mounted queries that fill a table the mutation changed. It learns which tables a query fills from what its `store` writes; a query that has not shown that yet is refetched to be safe, and so is every mounted query after a mutation with no `apply`.

List the queries yourself when the server changes more than `apply` does. Changing a cart line changes the order summary too, but a `GetOrderSummary` query that only fills an `OrderSummary` table is not refetched by default, because the mutation changed `CartLine`:

```ts
export default defineMutationHandler('SetCartLineQuantity', {
  apply: ({ db, variables }) => db.CartLine.update(variables.lineId, { quantity: variables.quantity }),
  refetch: ['GetCart', 'GetOrderSummary'],
})
```

The list replaces the default, so name every query that should be asked again, `GetCart` included.

## Where handlers run

`describe`, `apply`, `merge`, `reconcile` and `revert` run in a [web worker](/getting-started/configuration#handlersworker), off the main thread. They get `db` and `variables`, and can import whatever they need, but there is no Nuxt app there: no `useRoute()`, no `useState()`, no `window`. Pass what a handler needs in the mutation's variables, or keep it in a table. With `handlers.worker: false` they run on the page.

## The handler context

Every hook receives `{ db, variables }`. `apply` also gets `tempId`, and `reconcile` gets `tempIds` and `resolve`.

### `db`

The Dexie instance: one table per type your documents select with an id, any you declared with [`defineAirplaneStores`](/guide/stores-and-query-handlers), and the module's `queries`, `mutations` and `meta` tables. Every table is typed through the global `NuxtAirplaneStores` interface.

### `variables`

The variables the mutation was queued with, typed from the mutation document. In `reconcile` they are the variables as sent, with any temp id already replaced by its server id.

### `tempId()` (apply only)

Returns a placeholder id (`tmp-` plus a UUID) for a row the server will assign an id to. Call it once per row you create. The ids are stored on the outbox row, so when `apply` is run again on fresh server data (see [Two layers](/guide/stores-and-query-handlers#two-layers)) the same ids come back in the same order and the local rows keep their identity. A mutation queued later with one of them in its variables depends on this one: see [Chains](/guide/mutations#chains).

### `tempIds` and `resolve()` (reconcile only)

`tempIds` lists the ids `apply` minted, in call order. `resolve(tempId, id)` records that the placeholder now stands for the server's `id`: the row under the placeholder is re-keyed, in whichever table holds it, and every queued mutation that carries the placeholder is rewritten to the real id. Forgetting to call it fails those mutations with a message that says so, instead of sending the placeholder to the server.

## Organizing handler files

Everything under `app/airplane/` is scanned, at any depth, and every default export created with a `define*` helper is registered: handlers, stores and [`defineAirplaneRequest`](/guide/auth-and-headers). Two layouts work well:

**One file per operation**, with the singular helpers. No index needed; each file is picked up on its own. The [`handlers.generate`](/getting-started/configuration#handlersgenerate) option writes these files for you, with empty hooks, for every operation that has no handler yet.

```
app/airplane/
  stores.ts
  mutations/
    archive-site.ts      → export default defineMutationHandler('ArchiveSite', { … })
    rename-site.ts
```

**One file per operation, composed in an index.** A folder with an `index.ts` is treated as a unit: only the index is imported, so the pieces don't register twice.

```
app/airplane/
  queries/
    get-sites.ts         → export default defineQueryHandler('GetSites', { … })
    get-items.ts
    index.ts             → export default defineQueryHandlers({ ...getSites, ...getItems })
```

Shared lookups belong in `app/utils/`, which Nuxt auto-imports; types such as `AirplaneDexie` come from `#nuxt-airplane`.

Every default export in the directory must be the result of a `define*` helper. One that visibly isn't (an object or array literal, a function, a call to something else) **fails the build** with the file name, so a forgotten wrapper can't silently drop a handler. A default export the build can't see through (an identifier, `export default handlers`) is checked at runtime instead and ignored with a console warning if it isn't tagged.

## How rollback works

While `apply` runs, a Dexie middleware watches every write — `put`, `add`, `update`, `delete`, on any table except the module's own — and notes each row it changed. The first time the queue changes a row, the row as the server has it is set aside. There is no per-mutation undo log.

`rollback(id)` drops the mutation and puts its rows back to the server's version. If another queued mutation changed the same rows, or depends on it, the whole queue is taken off and put back on without it, so the others land on the restored data. A mutation that [depended on it](/guide/mutations#chains) and has nothing left to do is dropped with it. It covers every table, which is why most handlers never need `revert`.

## Reading other data

A handler can read anything in the database. The playground's `AddSiteItem` looks up the item's name in the `Item` table, filled by the catalog queries, so the new entry renders with a name before the server has seen it:

```ts
AddSiteItem: {
  async apply({ db, variables }) {
    const name = (await db.Item.get(variables.itemId))?.name ?? variables.itemId
    await db.Site.update(variables.siteId, (site) => {
      site.items = [...site.items, { id: variables.itemId, name, onHand: variables.onHand ?? 0 }]
    })
  }
}
```
