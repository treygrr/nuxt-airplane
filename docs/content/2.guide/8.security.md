The module keeps a copy of your API's data in the user's browser and replays their changes later. That is the point, and it has consequences worth knowing.

## What the module guarantees

- **Operations are static.** Queries and mutations are compiled from your `.gql` files at build time and sent verbatim with JSON variables. There is no string interpolation into GraphQL, so there is no GraphQL injection surface in the client.
- **Credentials are never persisted.** Headers are computed by your `defineAirplaneRequest` function at send time and are not written to IndexedDB or anywhere else. The outbox stores a mutation's document name, variables, description and undo log, nothing from the request layer.
- **`credentials` defaults to same-origin.** Cookies are only sent cross-origin if you opt in with `credentials: 'include'`.
- **Build-time secrets stay on the build machine.** `schemaHeaders` is read during the build and is not part of the runtime config. `headers`, `endpoint`, `dbName` and `cacheKey` *are* public runtime config, shipped to the browser.
- **Requests time out** (30 s by default, `timeout` in `defineAirplaneRequest`), so a hung request cannot hold the sync loop for the rest of the session.
- Nothing is rendered by the module, so it introduces no HTML injection surface of its own.

## What lives in the browser

Everything the module caches is in IndexedDB, unencrypted, under your app's origin:

- cached query responses (or the rows your `store` handlers wrote),
- the outbox: every pending mutation with its **variables** and a **description**, plus the before-images in its undo log,
- the cache key.

Treat it like any client-side storage: readable by anyone with access to the device profile and by any script running on your origin. In particular:

- **Clear it on sign-out.** `useAirplane().clear()` empties everything, including the outbox; `clearCache()` keeps the outbox. Without this, the next user of the same browser profile can read the previous user's data offline.
- **Don't queue what you wouldn't store.** Mutation variables sit in the outbox until they are sent. A "change password" mutation queued offline means the new password sits in IndexedDB until the connection returns. Keep such operations online-only (gate the UI on `useSync().online`, give them no handler) rather than queued.
- **Shared origins share a database.** `dbName` is per origin; if several apps live on one origin, give each its own name.

## Untrusted input

- **Server error messages** are stored on failed outbox rows (`error`) and exposed through `useSync().pending`. They come from the API; render them as text, never with `v-html`.
- **`describe` output** is whatever your handler returns; if it interpolates server data, the same applies.
- **Cached data is as trustworthy as your API**, no more. The module does not validate response shapes against the schema at runtime; a `store`/`read` handler should not assume more than the types promise.

## Network

- Use HTTPS for `endpoint`. A relative endpoint inherits the page's origin.
- Cross-origin cookie auth needs the API to answer with `Access-Control-Allow-Credentials: true` and an explicit origin.
- `onResponse` sees every response, including those of mutations synced in the background; a 401 handler there covers both.

## Retries and idempotency

The outbox retries on network failure and re-sends rows that were in flight when a tab closed. A mutation can therefore reach the server **more than once** if the first attempt succeeded but the response never arrived. Make mutations idempotent server-side where it matters (an `idempotency-key` header derived from the outbox row is a good pattern: `headers: ({ kind, variables, document }) => …`), or accept at-least-once semantics.

## Cache busting and schema changes

Changing `cacheKey` (or any `.gql` document) wipes cached data on the next load but keeps the outbox. If a deploy makes old queued mutations invalid, they will fail and can be rolled back by the user; they are not silently dropped. If the IndexedDB schema itself can no longer be opened (a lowered store version), the module recreates the database, which **does** drop the outbox; bump `version` instead of lowering it.

## Reporting

Security issues: open a private advisory on the GitHub repository rather than a public issue.
