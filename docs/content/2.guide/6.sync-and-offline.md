`useSync()` exposes the state of the mutation queue and the controls around it.

```vue
<script setup lang="ts">
const {
  online, syncing, synced, pending, syncTotal, syncCount, lastError,
  sync, rollback, retry, goOffline, goOnline
} = useSync()
</script>

<template>
  <header>
    <strong>{{ online ? 'Online' : 'Offline' }}</strong>
    <span v-if="syncing">Syncing {{ syncCount }} / {{ syncTotal }}…</span>
    <span v-else-if="synced">Synced</span>
    <span v-else>{{ pending.length }} pending</span>
  </header>
</template>
```

## The sync loop

The queue is sent whenever:

- a mutation is queued while online,
- the browser fires `online`,
- `goOnline()` is called,
- `sync()` is called,
- the app starts (to drain anything left from a previous session).

A trigger that arrives while a batch is being sent does not join that batch but starts another run as soon as it ends, so a mutation queued mid-batch goes out right after it. `sync()` resolves once the queue is drained or blocked.

Mutations go out oldest first. For each one the loop replaces any [placeholder id](/guide/mutations#creating-offline-then-editing) in the variables with the server id it was resolved to, sends the request, runs the [`reconcile` handler](/guide/mutation-handlers#reconcile), removes it from the queue and bumps `syncCount`. After the batch, the queries named in the handlers' [`refetch`](/guide/mutation-handlers#refetch) lists are refetched, or, for a handler with no list, the mounted queries that fill a table the mutation changed, and any that have not yet shown which tables they fill. A mutation with no `apply`, or whose `apply` changed nothing, refetches every mounted `useAirplaneQuery`.

### Side by side

Mutations that have nothing to do with each other are sent at the same time, up to four at once, so a long queue drains in a fraction of the round trips. Order is kept wherever it means something:

- a [chain](/guide/mutations#chains) goes in order: a mutation waits for the ones it depends on;
- two mutations that changed the **same row** go in the order they were made, whichever fields they wrote;
- a mutation with no `apply`, or whose `apply` changed nothing, could be about anything. It waits for everything queued before it, and everything after waits for it. An app without `apply` handlers syncs one mutation at a time, as before.

"Nothing to do with each other" is judged by your tables, so it holds on the server only if the API is cut the same way. The shape that fits is **one mutation per thing**: each changes its own record and nothing else.

```graphql
# Each touches one line. Two of them can land in any order, or at once.
mutation UpdateCartLineItem($lineId: ID!, $quantity: Int!) {
  updateCartLineItem(lineId: $lineId, quantity: $quantity) { id quantity }
}
```

```ts
// Offline, two lines are changed
mutate({ lineId: 'l1', quantity: 2 }) // apply writes CartLine l1
mutate({ lineId: 'l2', quantity: 5 }) // apply writes CartLine l2
```

Two rows locally and two records on the server, so sending both together is safe, and each can fail, retry or be rolled back without the other.

What does not fit is one `updateCart` mutation that takes the whole cart, or a large input covering many lines, for every small edit. On the server each call reads the cart, changes it and writes it back, so two of them at once can lose an edit or fail a version check. Locally they also all change the same `Cart` row, so they queue behind each other and nothing is gained. If the API is yours, split it into mutations per line; that is the fix.

When the API is not yours to change and cannot take concurrent mutations from one client, send them one at a time with [`concurrency`](/api/define-airplane-request):

```ts [app/airplane/request.ts]
export default defineAirplaneRequest({ concurrency: 1 })
```

The mutations then go one at a time. One that waits on an earlier one (a chain, the same row) may be passed by an unrelated one queued after it. A higher number than the default four is rarely worth it: browsers cap the connections to one host.

A network error stops a batch; a rejected mutation holds back only its chain:

- **A network error** sets `lastError`, leaves the mutation `pending` and stops: nothing more is started, and what is already in flight is left to land. The next trigger resumes from there, and so does the module [on its own](#retrying).
- **An answer about the session or the server**, not about the mutation, is treated the same way: an expired token or a busy server would reject everything queued behind it too. By default that is HTTP 401, 429 and 5xx, and the error codes `UNAUTHENTICATED`, `TOO_MANY_REQUESTS` and `RATE_LIMITED`; [`retryLater`](/guide/auth-and-headers#errors-that-are-not-about-the-mutation) changes the rule. An HTTP error with no GraphQL `errors` in its body always stops the sync, whatever its status: `retryLater` only sees answers that carry `errors`.
- **GraphQL errors**, or a placeholder id that was never resolved, mark that mutation `failed` with the message. The batch goes on, except for the mutations that [depend on it](/guide/mutations#chains): an item added to a site whose creation failed would fail too, so it waits, unsent, until the create is retried or rolled back. So does a later edit of the same field, which must not overtake it. `blocked` counts the waiting mutations. Everything else keeps syncing.

## Multiple tabs

Every tab of the app shares the same database, so a change made in one tab shows up in the others through the live queries. The outbox is shared too, which is why only one tab drains it at a time: the sync loop takes a [Web Lock](https://developer.mozilla.org/docs/Web/API/Web_Locks_API) named after the database before sending. A tab that finds the lock taken waits its turn and then sends whatever is still queued, usually nothing. If the tab holding the lock is closed mid-batch, the browser releases the lock and the next tab picks up where it left off, re-queuing the row that was in flight.

`syncing` is `true` only in the tab doing the sending. Browsers without the Web Locks API (and insecure contexts, where it is unavailable) fall back to each tab syncing on its own.

## Pending changes

`pending` is a live list of the outbox rows, oldest first. Each row has `id`, `document`, `variables`, a human-readable `description` (from the handler's [`describe`](/guide/mutation-handlers#describe) hook, or the humanized document name), `status` (`pending` · `syncing` · `failed`), `createdAt`, `dependsOn` and `after` (the ids of the queued mutations it [depends on or must follow](/guide/mutations#chains)) and, for failed rows, `error`. Showing it to users lets them see what hasn't reached the server and act on it.

The list is read from the outbox whenever it changes. A short queue shows every change at once. Reading a queue of thousands takes a while, so while one is being filled or drained the list is refreshed every so often rather than after each change (it rests ten times as long as its last read took, two seconds at most), and it is always brought up to date once the changes stop.

`failed` is the part of that list the server refused, oldest first, for a banner or a count. Those rows stay queued until they are [retried](#retrying) or [rolled back](#rolling-back).

A pending row whose chain holds a failed mutation is waiting on it. `blocked` counts them; to mark them in the list, walk the chain the way the module does:

```ts
const held = computed(() => {
  const ids = new Set(failed.value.map(m => m.id))
  for (const m of pending.value) if ([...(m.dependsOn ?? []), ...(m.after ?? [])].some(id => ids.has(id))) ids.add(m.id)
  return ids
})
```

## Rolling back

`rollback(id)` undoes a queued mutation and removes it from the queue, together with the mutations that [depend on it](/guide/mutations#chains) and have nothing left to do without it. Roll back the creation of a site and the items added to it offline go with it; roll back one of those items and the site stays.

The mutation's rows go back to the server's version. If another queued mutation changed the same rows or depends on it, the queue is taken off the tables and put back on without it, so the others still apply and stay undoable themselves. A dependent is dropped when it carries a placeholder that will now never resolve, or when applying it again changes nothing, such as a quantity set on an item that is gone. One that still does something stays queued on its own: a corrected save of the same new row, for example. A `revert` handler, if there is one, runs first.

`rollback` resolves with the mutations it dropped, and `dependents(id)` lists the ones that depend on it, so the UI can say so first:

```vue
<button @click="rollback(m.id)">
  Roll back<template v-if="dependents(m.id).length"> and {{ dependents(m.id).length }} more</template>
</button>
```

Say a user, offline, changes a quantity and then removes an item. Rolling back the quantity change puts the old quantity back while the removal stays applied.

A mutation that is being sent right now (`syncing`) cannot be rolled back. One queued before it can, and the one in flight keeps its change.

## Retrying

`retry(id)` puts a `failed` mutation back to `pending` and syncs; the mutations waiting on it go out right after it, in order. Rolling a failed mutation back drops the ones that cannot go on without it and releases the rest.

A sync that the network or the server stopped needs no one to restart it. The module tries again by itself after about a second, then two, then four, up to five minutes, with some randomness so that many clients do not come back at the same moment. When the answer carried a `Retry-After` header, that is how long it waits instead (an hour at most). `retryAt` holds the time of the next attempt, for a "retrying in 8 s" label, and is `null` when none is planned. Any other trigger, such as `sync()` or the browser's `online` event, still syncs at once.

### Idempotency keys

A request can reach the server and its answer still get lost, so a retry may send a mutation the server has already applied. Every queued mutation therefore carries a key, a UUID made when it is queued and the same on every attempt. It is sent in the request's `extensions`:

```json
{ "query": "mutation …", "variables": { … }, "extensions": { "idempotencyKey": "3f0c…" } }
```

A server that remembers the keys it has seen can answer a repeat with the first result instead of applying it twice. The key is on the outbox row (`idempotencyKey`) and in the request context, for an API that wants it as a header:

```ts [app/airplane/request.ts]
export default defineAirplaneRequest({
  headers: ctx => (ctx.idempotencyKey ? { 'Idempotency-Key': ctx.idempotencyKey } : undefined),
})
```

Mutations sent with [`queue: false`](/guide/mutations#online-only-mutations) get a key too, a new one per call.

## Going offline on purpose

`goOffline()` holds the client offline whatever the network says: queries are read from the tables only and mutations stay queued. `goOnline()` releases the hold and syncs. Use it for a "work offline" switch, or to test offline behaviour without touching devtools.

`online` is the effective state. `networkOnline` (what the browser reports) and `forcedOffline` (whether `goOffline()` is in effect) expose the two inputs.

### The choice is kept

A user who chose to work offline, on a metered connection say, stays offline until they choose otherwise:

- **Across reloads.** The choice is kept in `localStorage`, per database, and read before anything could be sent. A queue left from before the reload waits.
- **In every tab.** The tabs share one outbox, so one tab going online would send what another holds back. Going offline or back online in one tab does the same in the others at once.

Where `localStorage` cannot be used (blocked storage, some private modes), the choice holds for the page only.

Going offline while a batch is being sent lets the mutations already on their way land and starts no more.

### Starting offline

[`startOffline: true`](/getting-started/configuration#startoffline) starts the app held offline until the user chooses otherwise; their choice is kept and wins from then on.

For a choice the app makes at startup from its own state (a setting it loads, `navigator.connection.saveData`), call `goOffline()` from a plugin. Nothing is sent until the first page has hydrated, so the plugin always comes first, even when it awaits something before deciding:

```ts [app/plugins/offline.client.ts]
export default defineNuxtPlugin({
  dependsOn: ['nuxt-airplane'],
  async setup() {
    const { meteredMode } = await loadSettings()
    if (meteredMode) useAirplane()?.goOffline()
  },
})
```

On a page rendered on the server, `useSync()` reports what the server rendered (online, nothing queued) until the page has hydrated, so the two match, and the real state right after.
