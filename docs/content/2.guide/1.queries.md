`useAirplaneQuery` takes the name of a query document and returns reactive refs backed by the tables in IndexedDB.

```vue
<script setup lang="ts">
const { data, loading, fetching, error, updatedAt, refresh } = useAirplaneQuery('GetSites')
</script>
```

## Where the data comes from

`data` is not the network response. It is what the query's [`read` handler](/guide/stores-and-query-handlers) builds from the tables, kept live:

1. On mount the composable runs `read` inside Dexie's `liveQuery`. If the query has been fetched before, `data` is set immediately and `loading` becomes `false`.
2. If the app is online, a request is sent in the background. The response goes through the query's `store` handler into the tables, and `read` runs again.
3. Any later write to a table `read` touched — a refetch, or a [mutation handler](/guide/mutation-handlers) editing a row — updates `data` too.

Components that ask for the same query with the same variables at the same moment share one request.

This is what makes optimistic updates free: a handler edits a row once and every component showing a query that reads it re-renders.

A query without a `read` handler is served from the network: `data` is the last response while online, and `null` with an `error` while offline. For a query that is only ever answered by the server, a search or a report, [`useOnlineQuery`](/guide/online-queries) is the better fit: it asks only when you say, keeps nothing, and is rendered on the server.

## Variables

Variables can be a plain object, a ref or a getter. When they change the composable runs `read` with the new ones and fetches them.

```ts
const siteId = ref('site-1')
const { data } = useAirplaneQuery('GetSite', () => ({ id: siteId.value }))
```

Each distinct set of variables is fetched and recorded on its own. `undefined`, `null` and `{}` are treated as the same, empty set.

The query's handler can declare [local variables](/guide/stores-and-query-handlers#local-variables), filters the server does not know about. Pass them in the same object. They reach `read` and nothing else: they are never sent, and changing one runs `read` again without a fetch.

```ts
const { data } = useAirplaneQuery('GetSiteItems', () => ({ siteId: siteId.value, first: 50, lowStock: lowStockOnly.value }))
```

## Options

```ts
useAirplaneQuery('GetSites', undefined, { fetch: false })
```

| Option | Default | |
| --- | --- | --- |
| `fetch` | `true` | Set to `false` to only read the tables and never hit the network. |
| `enabled` | `true` | A boolean, ref or getter. While `false` the query does nothing: no `read`, no fetch, `data` is `null` and `loading` is `false`. |

The two say different things. `fetch: false` shows what is stored and never asks. `enabled: false` is for variables that are not known yet, such as a detail view waiting for its id: nothing runs, so `read` never sees an `undefined` id.

```ts
const id = computed(() => route.params.id as string | undefined)
const { data } = useAirplaneQuery('GetSite', () => ({ id: id.value! }), { enabled: () => !!id.value })
```

## Return value

| Field | Type | |
| --- | --- | --- |
| `data` | `Ref<Result \| null>` | Live data from the tables. |
| `loading` | `Ref<boolean>` | `true` until the tables have been read and, if online, the first fetch is done. |
| `fetching` | `Ref<boolean>` | `true` while a request is in flight. |
| `error` | `Ref<Error \| null>` | The last fetch error. |
| `updatedAt` | `Ref<number \| null>` | When this query was last fetched from the server. |
| `refresh` | `() => Promise<void>` | Fetch now. Does nothing while offline, or while not enabled. |

## Offline behaviour

While [offline](/guide/sync-and-offline), `refresh` is a no-op and `loading` stays `true` only if the query has never been fetched. Showing `updatedAt` is a good way to tell users how fresh the data is.

## Server-side rendering

The tables live in the browser, so during SSR `useAirplaneQuery` returns `data: null` and `loading: true` (`false` when not enabled). The initial fetch is deferred to `onMounted` so the client's first render matches the server's. A query whose answer should be in the server-rendered page is an [online query](/guide/online-queries#server-side-rendering).
