`useMutation` takes the name of a mutation document and returns a `mutate` function.

```vue
<script setup lang="ts">
const rename = useMutation('RenameSite')

async function save(id: string, name: string) {
  await rename.mutate({ id, name })
}
</script>
```

## What `mutate` does

1. Adds a row to the outbox with the document name and the variables you passed.
2. Runs the mutation's [`apply` handler](/guide/mutation-handlers), if there is one, so the cache (and every `useQuery` reading it) reflects the change immediately. The rows it touches are snapshotted so the change can be [rolled back](/guide/sync-and-offline#rolling-back).
3. Resolves with the outbox row.
4. Kicks the sync loop. If the app is online the mutation is sent right away; otherwise it waits.

`mutate` resolves as soon as the change is visible locally, not when the server has accepted it. That is the point: the UI never waits on the network.

When the server needs to answer before the UI can continue, pass `{ queue: false }`; see [Online-only mutations](#online-only-mutations).

## Return value

| Field | Type | |
| --- | --- | --- |
| `mutate` | `(variables) => Promise<MutationRow>` | Apply locally and queue. |
| `loading` | `Ref<boolean>` | `true` while `apply` runs. |
| `error` | `Ref<Error \| null>` | Error thrown by `apply`, if any. |

The resolved `MutationRow` has the queue `id`, which you can hand to `rollback(id)` from [`useSync()`](/guide/sync-and-offline).

## Server errors

If the server answers with GraphQL errors the mutation is marked `failed` and left in the queue, with the message in `error`. The user can `retry(id)` or `rollback(id)`. A network failure is different: the batch stops and everything stays `pending` for the next attempt.

## Ordering

The queue is sent oldest first, one mutation at a time, so dependent changes (create a site, then add an item to it) arrive in the order they were made.

## Creating offline, then editing

A row created offline has no server id yet, but the user can still rename it, add items to it or delete it before the connection is back. Those later mutations reference an id the server has never seen.

The module handles this with placeholder ids. In the create's `apply` handler, mint the id with `tempId()`; in its `reconcile`, tell the module what the server replaced it with:

```ts [app/airplane/mutations/create-site.ts]
export default defineMutationHandler('CreateSite', {
  apply: ({ db, variables, tempId }) =>
    db.sites.put({ id: tempId(), name: variables.name, archived: false }),
  reconcile: async ({ db, tempIds, resolve }, result) => {
    const [tmp] = tempIds
    const local = await db.sites.get(tmp)
    if (local) {
      await db.sites.delete(tmp)
      await db.sites.put({ ...local, id: result.createSite.id })
    }
    await resolve(tmp, result.createSite.id)
  },
  refetch: ['GetSites'],
})
```

Nothing else changes. The component reads the new row from the live query, with its `tmp-…` id, and calls `rename.mutate({ id, name })` as usual. When the queue is sent:

1. `CreateSite` goes out. Its `reconcile` swaps the local row to the real id and calls `resolve`.
2. Before `RenameSite` is sent, every occurrence of the placeholder in its variables, however deeply nested, is replaced by the real id. The outbox row is rewritten too, so a later re-apply targets the real row.
3. `RenameSite` reaches the server with the id it knows.

Placeholders are stable: if fresh server data arrives while the create is still queued, `apply` is re-run and `tempId()` hands out the same id, so the queued rename still points at the right row. Resolved ids are remembered (the last 1000) after the queue drains, so a component that still holds a placeholder it read earlier keeps working.

If a mutation is about to be sent with a placeholder that was never resolved, because the create failed or its `reconcile` did not call `resolve`, it is marked `failed` with a message saying which id, instead of being sent and rejected by the server.

::note
Coming from urql's graphcache offline exchange: this is the gap where an optimistic insert got a temporary id and a queued update on it failed on replay. Here the update is rewritten before it is sent.
::

## Online-only mutations

Some mutations cannot wait in a queue: a checkout, a payment, a form whose response the UI needs right away. Pass `{ queue: false }` and `mutate` sends the request now and resolves with the server's data:

```vue
<script setup lang="ts">
const checkout = useMutation('Checkout', { queue: false })

async function pay() {
  const { checkout: order } = await checkout.mutate({ cartId })
  await navigateTo(`/orders/${order.id}`)
}
</script>
```

With `queue: false`:

- Nothing is written to the outbox and no `apply` handler runs. `loading` is `true` while the request is in flight.
- The outbox is drained first, so the server sees every change queued before it (the cart the checkout is for).
- Placeholder ids in the variables are replaced the same way as for queued mutations.
- The handler's `reconcile` runs with the response, and the queries in its `refetch` list (or every mounted query) are refetched.
- It rejects while offline, and on GraphQL errors, with the error message. Nothing is retried.

The same call is available as `execute(name, variables)` on the client from [`useAirplane()`](/api/use-airplane).
