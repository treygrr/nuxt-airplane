Nothing is cached as a response. A query's data lives in tables, and a **query handler** is the wiring between the two: `store` writes a response into the tables, `read` builds the query's result from them. `useQuery` returns what `read` returns, online or offline, live. A mutation that edits a row shows up in every query reading it, a search typed while offline runs against what was fetched, and the tables and their row types come from your schema and documents, so there is nothing to declare.

A query without a handler is served from the network while online and has nothing to show offline. That is by design: the handler is where you decide what a query stores, and in development the module lists the queries that have none.

## Inferred tables

At build time the module looks at every selection in your documents. A type that is selected with its `id` field gets a table keyed on it, so with

```graphql
query GetSites { sites { id name archived items { id name onHand } } }
```

`db.Site` and `db.SiteItem` exist in every handler, typed as `Table<SiteRow>` and `Table<SiteItemRow>`. The row type is the union of the fields your documents select on that type: fields selected in every selection are required, the others optional, since a row stored by one query may lack a field only another query asks for. A nested entity selected with its id is typed as its own row, because that is how the response carries it; any other nested object is typed from the fields selected on it, by the same rule, never from the schema type:

```ts
type SiteRow = { id: string, name: string, archived?: boolean, items?: Array<SiteItemRow>, owner?: { name: string } | null }
type SiteItemRow = { id: string, name: string, onHand: number }
```

So a query's result is always assignable to the tables it came from, and `db.Site.bulkPut(data.sites)` type-checks with no cast.

Object types without an `id` (a connection, a page, a nested value object) get no table; they are stored wherever you put them.

A table only has what a `store` handler put in it. The inferred `db.SiteItem` above exists, typed and keyed, but stays empty unless a handler writes to it: the `GetSites` handler below keeps the items on the site row instead, as the response has them.

## Writing a handler

```ts [app/airplane/queries/get-sites.ts]
export default defineQueryHandler('GetSites', {
  store: ({ db }, data) => db.Site.bulkPut(data.sites),

  async read({ db, variables }) {
    const { archived, search } = variables ?? {}
    const q = search?.trim().toLowerCase()
    const sites = (await db.Site.toArray())
      .filter(s => archived == null || s.archived === archived)
      .filter(s => !q || s.name.toLowerCase().includes(q))
    return { sites }
  },
})
```

`store` receives the response typed as the query's result and runs inside a transaction over every table. `data.sites` and `SiteRow` come from the same selection, so the `bulkPut` type-checks with nothing declared.

`read` must return the query's result type, so `useQuery('GetSites')` has the same `data` type with or without a handler. It runs inside Dexie's `liveQuery`: whatever it reads is observed, and `data` updates whenever one of those tables changes. Both hooks receive the query's `variables`.

Either hook can stand alone:

- `read` without `store`, for a query whose rows another query already fills: a `GetSite` that reads `db.Site.get(variables.id)` after `GetSites` stored the list.
- `store` without `read`, for a query that only exists to fill a table for others. It is served from the network itself.

Rows are never deleted by a response, only upserted. A row that disappeared on the server stays in its table until a mutation handler deletes it, a `store` handler removes it, or the cache is cleared.

## Extra indexes and your own tables

`defineAirplaneStores` adds to what is inferred. For an inferred table, list the indexes a `read` handler sorts or filters on; the key is implied. Any other name declares a table of your own, in Dexie's [`stores()` syntax](https://dexie.org/docs/Version/Version.stores()).

```ts [app/airplane/stores.ts]
export default defineAirplaneStores({
  Item: 'name',
  drafts: '++id, siteId',
})
```

Your own tables are typed by augmenting `NuxtAirplaneStores`:

```ts
declare global {
  interface NuxtAirplaneStores {
    drafts: { id?: number, siteId: string, body: string }
  }
}
```

A `store` handler can write to a table of your own shape just as well, for example a join table keyed on two ids:

```ts [app/airplane/queries/get-sites.ts]
export default defineQueryHandler('GetSites', {
  async store({ db }, data) {
    await db.Site.bulkPut(data.sites.map(({ items, ...site }) => site))
    await db.siteItems.bulkPut(data.sites.flatMap(site =>
      site.items.map(item => ({ siteId: site.id, itemId: item.id, name: item.name, onHand: item.onHand }))))
  },
  async read({ db }) {
    const [sites, siteItems] = await Promise.all([db.Site.toArray(), db.siteItems.toArray()])
    return {
      sites: sites.map(site => ({
        ...site,
        items: siteItems.filter(si => si.siteId === site.id).map(si => ({ id: si.itemId, name: si.name, onHand: si.onHand })),
      })),
    }
  },
})
```

::note
Adding a table or an index needs no version bump: Dexie 4 reconciles the schema on open. Pass `{ version: 2 }` as the second argument when you change an existing table's primary key or want an explicit migration. If the stored database cannot be opened with the declared schema (for example after lowering the version), the module logs a warning and recreates it.
::

::tip
IndexedDB cannot use booleans as index keys, so an index on `archived` matches nothing; filter booleans in JavaScript, or store flags you want to index as `0 | 1` in a table of your own. In development the module warns in the console the first time a boolean is written to an indexed key.
::

## Variables

Each set of variables is its own request and its own `updatedAt`, but they all read the same tables, so a filter the server has never seen still works offline against what was stored. The flip side: a filtered response cannot tell you about deletions outside its scope, so keep one broad fetch around (an unfiltered query, or `refetch: ['GetSites']` after sync) to reconcile.

## Pagination

A Relay-style connection fits the same pattern. `store` puts the nodes of each page in their table, and `read` rebuilds the page from it using the same cursor logic as the server. If cursors are derived from the row itself (for example a base64 of the sort key and id) rather than from a server-side offset, the local read paginates identically, and a user can keep paging offline through whatever has been fetched.

```ts
SearchItems: {
  store: ({ db }, data) => db.Item.bulkPut(data.searchItems.edges.map(edge => edge.node)),
  async read({ db, variables }) {
    const { query, first = 20, after } = variables
    const all = (await db.Item.orderBy('name').toArray()).filter(i => !query || i.name.includes(query))
    const start = after ? all.findIndex(i => cursorOf(i) === after) + 1 : 0
    const page = all.slice(start, start + first)
    return {
      searchItems: {
        edges: page.map(node => ({ cursor: cursorOf(node), node })),
        totalCount: all.length,
        pageInfo: { hasNextPage: start + first < all.length, endCursor: page.length ? cursorOf(page.at(-1)!) : null },
      },
    }
  },
}
```

In the UI, give each page its own `useQuery` (a small component per page works well) and push the previous page's `endCursor` to load the next one. `hasNextPage` and `totalCount` reflect local data while offline, so they can differ from the server's until you're back online.

Classic numbered pages work the same way with `page` / `pageSize` variables: `read` slices the sorted local rows at `(page - 1) * pageSize`. Offset pages are only accurate offline for pages that were fetched; an unvisited page shows whatever local data sits at that offset.

## Prefetching every page

A paginated query only stores the pages a user visits. Opt it into `prefetch` and, after any page is fetched, the module keeps requesting the next one in the background until there are none left, storing each page through `store`. The whole set is then available offline.

`next` receives the page just fetched and its variables and returns the next page's variables, or `null` at the end. That covers Relay connections and numbered pages alike:

```ts
// Relay: follow the end cursor
SearchItems: {
  prefetch: {
    next: (data, variables) => data.searchItems.pageInfo.hasNextPage
      ? { ...variables, after: data.searchItems.pageInfo.endCursor }
      : null,
  },
  store,
  read,
}

// Numbered pages: page + 1 until the last
ItemsPage: {
  prefetch: {
    next: (data, variables) => data.itemsPage.page < data.itemsPage.totalPages
      ? { ...variables, page: data.itemsPage.page + 1 }
      : null,
  },
  store,
  read,
}
```

Options: `maxPages` caps a run (default 1000); `when` is checked before each run, so app state can decide what deserves to be cached:

```ts
prefetch: {
  next: …,
  when: () => useSettings().cacheCatalog && !navigator.connection?.saveData,
}
```

One run per document at a time; it stops when the app goes offline or a request fails, and pending mutations are re-applied once at the end. `useSync().prefetching` counts the runs in progress, handy for a "caching for offline…" notice.

### Features that shouldn't work offline

The opposite case, a search that must always hit the server (an invoice lookup, say), needs no module option: leave the query without a handler. It is served from the network while online; offline, `data` stays `null` and `error` says why, so gate the UI on `useSync().online`.

```vue
<script setup lang="ts">
const { online } = useSync()
</script>

<template>
  <InvoiceSearch v-if="online" />
  <p v-else>Invoice search needs a connection.</p>
</template>
```

## Mutations against tables

Mutation handlers get the same `db` and write to it directly. Every query whose `read` touches the row follows:

```ts [app/airplane/sites.ts]
export default defineMutationHandlers({
  RenameSite: {
    // GetSites and GetSite both update
    apply: ({ db, variables }) => db.Site.update(variables.id, { name: variables.name }),
  },
  DeleteSite: {
    // Leaves every list that showed it
    apply: ({ db, variables }) => db.Site.delete(variables.id),
  },
  RemoveSiteItem: {
    // Nested data is plain data on the row
    apply: ({ db, variables }) => db.Site.update(variables.siteId, (site) => {
      site.items = site.items.filter(item => item.id !== variables.itemId)
    }),
  },
})
```

Shared helpers can import the module's types from `#nuxt-airplane` (for example `AirplaneDexie`, the typed Dexie instance).

Rollback keeps working without a `revert` handler: every write made during `apply`, to any table, is recorded by an undo log. See [Mutation handlers](/guide/mutation-handlers#how-rollback-works).

## Rebase on refetch

A fresh response overwrites the fields it carries, which would wipe local changes that haven't reached the server yet. So after every successful fetch the module re-applies the pending mutations, oldest first, on top of the new data. Keep `apply` idempotent with respect to its own result (set a value rather than increment it) and this is invisible.

## Cache busting

Local data outlives deploys, so a release that changes what a query returns or how a table is shaped needs a way to start over. The module keeps a **cache key** in the database: the [`cacheKey`](/getting-started/configuration#cachekey) option (a git SHA, a build id) plus a hash of the compiled GraphQL documents. On startup, if the stored key differs from the current one, every table except the outbox is emptied, along with the fetch records, and the key is updated. Fetches and mutations wait for that check, so nothing is written under a stale key.

The **outbox is kept**: changes a user made offline before the redeploy still sync, and are re-applied on top of the fresh data as it arrives. If a release makes old pending mutations invalid, that is the moment to also bump the Dexie store `version` or let them fail and be rolled back.

To wipe programmatically, for example on sign-out, use `useAirplane()`: `clearCache()` empties the tables and keeps the outbox; `clear()` empties everything.

## When to use which

| | `store` + `read` | `read` only | `store` only | No handler |
| --- | --- | --- | --- | --- |
| Works offline | Yes | Yes, from rows other queries stored | No | No |
| Follows local edits | Yes | Yes | No | No |
| Filtering, sorting, search offline | Any, from the tables | Any, from the tables | – | – |
| Use for | Most queries | A detail view over a stored list | Filling a table for other queries | A lookup that must hit the server |
