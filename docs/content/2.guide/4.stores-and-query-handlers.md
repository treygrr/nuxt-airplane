Nothing is cached as a response. A query's data lives in tables, and a **query handler** is the wiring between the two: `store` writes a response into the tables, `read` builds the query's result from them. `useQuery` returns what `read` returns, online or offline, live. A mutation that edits a row shows up in every query reading it, a search typed while offline runs against what was fetched, and the tables and their row types come from your schema and documents, so there is nothing to declare.

A query without a handler is served from the network while online and has nothing to show offline. That is by design: the handler is where you decide what a query stores, and in development the module lists the queries that have none.

## Inferred tables

At build time the module looks at every selection in your documents. A type that is selected with its `id` field gets a table keyed on it, so with

```graphql
query GetSites { sites { id name archived items { id name onHand } } }
```

`db.Site` and `db.SiteItem` exist in every handler, typed as `Table<SiteRow>` and `Table<SiteItemRow>`. The row type is the union of the fields your documents select on that type, and it follows the selections at every level:

- A field is **required** when every selection that returns a full node of the type selects it, **optional** otherwise, since a row stored by one query may lack a field only another query asks for.
- A selection that only navigates through the type to what is below it, such as `site { id items { id name } }` or `site { id items { totalCount nodes { id } } }`, or selects nothing but `id`, as a mutation result often does, never stores a full row. It adds its fields to the row but does not make the others optional. The rule is that it selects no scalar or enum field other than `id`; object children of any kind, an entity, a connection, an embedded object, do not count.
- A nested entity selected with its id is typed as its own row, because that is how the response carries it. Any other nested object is typed from the fields selected on it, by the same rule, never from the schema type.
- A union or interface becomes one object per type condition, plus the common fields alone when the conditions do not cover every member, the same shape the generated result types have.

```ts
type SiteRow = { id: string, name: string, archived?: boolean, items?: Array<SiteItemRow>, owner: { name: string, email?: string } | null }
type SiteItemRow = { id: string, name: string, onHand: number }
```

So a query's result is always assignable to the tables it came from, and `db.Site.bulkPut(data.sites)` type-checks with no cast. In the other direction, a `read` that returns rows compiles as long as the query selects only required fields. An optional field on a row is a fact about your documents: some query stores the type without it, so a `read` for a query that needs it has to decide what to show when it is missing. Do that visibly, with a default or a filter, rather than with a cast; or give the queries the same selection through a shared fragment, and the field becomes required.

Object types without an `id` (a connection, a page, a nested value object) get no table; they are stored wherever you put them.

A table only has what a `store` handler put in it, and the module only creates the inferred tables your app uses. `db.SiteItem` above is typed in every handler, but if nothing mentions it, as with the `GetSites` handler below, which keeps the items on the site row as the response has them, no object store is opened for it.

"Mentions" is read off your source at build time: the name anywhere in a file of the handlers directory (`db.SiteItem`, a key of `defineAirplaneStores`), or reached as `.SiteItem` or `'SiteItem'` in the rest of the app. A table you only reach by a computed name is not found that way and throws an error that says so; list it in [`defineAirplaneStores`](#extra-indexes-and-your-own-tables) (`SiteItem: ''`) to have it created.

## Writing a handler

A handler is a file in the handlers directory. Write it by hand, or let [`handlers.generate`](/getting-started/configuration#handlersgenerate) create one per query with empty `store` and `read` hooks to fill in.

```ts [app/airplane/queries/get-sites.ts]
export default defineQueryHandler('GetSites', {
  store: ({ db }, data) => db.Site.bulkPut(data.sites),

  async read({ db, variables }) {
    const { archived, search } = variables ?? {}
    const q = search?.trim().toLowerCase()
    const sites = (await db.Site.toArray())
      .filter(s => archived == null || s.archived === archived)
      .filter(s => !q || s.name.toLowerCase().includes(q))
    return { sites }
  },
})
```

`store` receives the response typed as the query's result and runs inside a transaction over every table. `data.sites` and `SiteRow` come from the same selection, so the `bulkPut` type-checks with nothing declared.

::warning
Like `apply`, `store` should only await Dexie operations. Awaiting a `fetch` or a timer commits the transaction early: the rest of the response is not stored and the fetch fails.
::

`read` must return the query's result type, so `useQuery('GetSites')` has the same `data` type with or without a handler. It runs inside Dexie's `liveQuery`: whatever it reads is observed, and `data` updates whenever one of those tables changes. Both hooks receive the query's `variables`.

Either hook can stand alone:

- `read` without `store`, for a query whose rows another query already fills: a `GetSite` that reads `db.Site.get(variables.id)` after `GetSites` stored the list.
- `store` without `read`, for a query that only exists to fill a table for others. It is served from the network itself.

Rows are never deleted by a response, only upserted. A row that disappeared on the server stays in its table until a mutation handler deletes it, a `store` handler removes it, or the cache is cleared.

`store` runs in a [web worker](/getting-started/configuration#handlersworker), so a large response does not hold up the page; `read` runs on the page, inside the live query. A `store` therefore cannot use Nuxt composables or the DOM. It needs neither: it gets the response and writes it down.

## Extra indexes and your own tables

`defineAirplaneStores` adds to what is inferred. For an inferred table, list the indexes a `read` handler sorts or filters on; the key is implied. Any other name declares a table of your own, in Dexie's [`stores()` syntax](https://dexie.org/docs/Version/Version.stores()).

```ts [app/airplane/stores.ts]
export default defineAirplaneStores({
  Item: 'name',
  drafts: '++id, siteId',
})
```

Your own tables are typed by augmenting `NuxtAirplaneStores`:

```ts
declare global {
  interface NuxtAirplaneStores {
    drafts: { id?: number, siteId: string, body: string }
  }
}
```

A `store` handler can write to a table of your own shape just as well, for example a join table keyed on two ids:

```ts [app/airplane/queries/get-sites.ts]
export default defineQueryHandler('GetSites', {
  async store({ db }, data) {
    await db.Site.bulkPut(data.sites.map(({ items, ...site }) => site))
    await db.siteItems.bulkPut(data.sites.flatMap(site =>
      site.items.map(item => ({ siteId: site.id, itemId: item.id, name: item.name, onHand: item.onHand }))))
  },
  async read({ db }) {
    const [sites, siteItems] = await Promise.all([db.Site.toArray(), db.siteItems.toArray()])
    return {
      sites: sites.map(site => ({
        ...site,
        items: siteItems.filter(si => si.siteId === site.id).map(si => ({ id: si.itemId, name: si.name, onHand: si.onHand })),
      })),
    }
  },
})
```

::note
Adding a table or an index needs no version bump: Dexie 4 reconciles the schema on open. Pass `{ version: 2 }` as the second argument when you change an existing table's primary key or want an explicit migration. If the stored database cannot be opened with the declared schema (for example after lowering the version), the module logs a warning and recreates it.
::

::tip
IndexedDB cannot use booleans as index keys, so an index on `archived` matches nothing; filter booleans in JavaScript, or store flags you want to index as `0 | 1` in a table of your own. In development the module warns in the console the first time a boolean is written to an indexed key.
::

## The schema file

The tables are put together from three places: the types your documents select with an `id`, what `defineAirplaneStores` adds, and the module's own. To see the result without opening devtools, read `.nuxt/nuxt-airplane/schema.ts`. It holds every table the app opens, in Dexie's `stores()` syntax, the primary key first and then the indexes, with a note saying where each comes from:

```ts [.nuxt/nuxt-airplane/schema.ts]
export const version = 1

export const schema = {
  // Inferred: a type your documents select with its `id`, keyed on it
  Item: '&id, name', // indexes from airplane/stores.ts
  Site: '&id',
  // Declared with defineAirplaneStores
  drafts: '++id, siteId', // airplane/stores.ts
  // The module's own: fetch records, the outbox, bookkeeping, the server's version of queued rows
  queries: '&key, document, updatedAt',
  mutations: '++id, status, createdAt, document, unkeyed, *rows, *creates, *writes, *tempIds',
  meta: '&key',
  base: '[table+key]',
} as const

/** Types your documents select with an `id` that get no table, because nothing in the app mentions them. */
export const unused = ['Owner'] as const
```

It is the same merge the app does when it opens the database, so what it says is what is created. To read what `defineAirplaneStores` declares, the build runs those files, and only those: a file whose default export is `defineAirplaneStores(…)`. One that cannot run at build time, because it reaches something only the browser has, is named in the file and left out of it.

It is written when the app is prepared, built or started, and again when a GraphQL document or the schema changes, since that is what decides the inferred tables. A change to `defineAirplaneStores` alone shows at the next of those; in development the console says when the file has fallen behind.

Set [`database.schemaFile`](/getting-started/configuration#databaseschemafile) to write it into your app as well and commit it. A change to the tables then shows up in review like any other change.

## Variables

Each set of variables is its own request and its own `updatedAt`, but they all read the same tables, so a filter the server has never seen still works offline against what was stored. The flip side: a filtered response cannot tell you about deletions outside its scope, so keep one broad fetch around (an unfiltered query, or `refetch: ['GetSites']` after sync) to reconcile.

## Local variables

Some filters exist only on the client: "low stock" (`onHand < min`) on a list of items, say, when the server has no such argument. The operation cannot declare a variable it does not use, and a variable the server does not know should not be sent. Declare it on the handler instead, with its default:

```ts [app/airplane/queries/get-site-items.ts]
export default defineQueryHandler('GetSiteItems', {
  local: { lowStock: false },
  store: ({ db }, data) => db.SiteItem.bulkPut(data.siteItems.edges.map(e => e.node)),
  async read({ db, variables, local }) {
    const { siteId, first = 50, after } = variables
    const rows = (await db.SiteItem.where('siteId').equals(siteId).toArray())
      .filter(i => !local.lowStock || i.onHand < i.min)
    return { siteItems: connection(rows, decodeCursor(after), first) }
  },
})
```

The caller passes it with the query's own variables:

```ts
const { data } = useQuery('GetSiteItems', () => ({ siteId, first: 50, lowStock: lowStockOnly.value }))
```

The module sorts the keys against the operation. Those it declares are the query's variables: they are sent, make up the query key, and reach `store`, `prefetch` and `read` as `variables`. Those in the handler's `local` go to `read` alone, as `local`, with the defaults filled in for any that were left out or `undefined`. A key that is neither is dropped rather than sent, with a warning in development.

So a local variable:

- **is never sent**, and is not part of the fetch record, the in-flight request or the persisted query hash;
- **fetches nothing when it changes.** `read` runs again against the tables, `loading` stays `false`, and it works the same offline;
- **is shared nothing by.** Two `useQuery` calls with the same query variables and different local ones share one fetch and one fetch record, and each gets its own `read`.

It filters what has been stored, nothing more. For a complete answer, pair it with [`prefetch`](#prefetching-every-page) or a broad fetch, and work out counts such as `totalCount` from the rows, since the server's count is of everything.

The `local` object is the variables' type too: `{ lowStock: false }` makes `lowStock` a `boolean`, in `read` and at every `useQuery('GetSiteItems', …)`. A literal widens, so give a union or an enum its type with `as`: `{ sort: 'NAME' as SiteItemSort }`. A local name may not be one the operation declares; that is a type error. Passing a key that is neither is a type error in an object literal; inside a getter, TypeScript does not check for extra keys, which is what the development warning is for.

Only `read` gets local variables, so a handler that declares them without a `read` gets a warning in development: they would do nothing.

## Pagination

A Relay-style connection fits the same pattern. `store` puts the nodes of each page in their table, and `read` rebuilds the page from it using the same cursor logic as the server. If cursors are derived from the row itself (for example a base64 of the sort key and id) rather than from a server-side offset, the local read paginates identically, and a user can keep paging offline through whatever has been fetched.

```ts
SearchItems: {
  store: ({ db }, data) => db.Item.bulkPut(data.searchItems.edges.map(edge => edge.node)),
  async read({ db, variables }) {
    const { query, first = 20, after } = variables
    const all = (await db.Item.orderBy('name').toArray()).filter(i => !query || i.name.includes(query))
    const start = after ? all.findIndex(i => cursorOf(i) === after) + 1 : 0
    const page = all.slice(start, start + first)
    return {
      searchItems: {
        edges: page.map(node => ({ cursor: cursorOf(node), node })),
        totalCount: all.length,
        pageInfo: { hasNextPage: start + first < all.length, endCursor: page.length ? cursorOf(page.at(-1)!) : null },
      },
    }
  },
}
```

In the UI, give each page its own `useQuery` (a small component per page works well) and push the previous page's `endCursor` to load the next one. `hasNextPage` and `totalCount` reflect local data while offline, so they can differ from the server's until you're back online.

Classic numbered pages work the same way with `page` / `pageSize` variables: `read` slices the sorted local rows at `(page - 1) * pageSize`. Offset pages are only accurate offline for pages that were fetched; an unvisited page shows whatever local data sits at that offset.

## Prefetching every page

A paginated query only stores the pages a user visits. Opt it into `prefetch` and, after any page is fetched, the module keeps requesting the next one in the background until there are none left, storing each page through `store`. The whole set is then available offline.

`next` receives the page just fetched and its variables and returns the next page's variables, or `null` at the end. That covers Relay connections and numbered pages alike:

```ts
// Relay: follow the end cursor
SearchItems: {
  prefetch: {
    next: (data, variables) => data.searchItems.pageInfo.hasNextPage
      ? { ...variables, after: data.searchItems.pageInfo.endCursor }
      : null,
  },
  store,
  read,
}

// Numbered pages: page + 1 until the last
ItemsPage: {
  prefetch: {
    next: (data, variables) => data.itemsPage.page < data.itemsPage.totalPages
      ? { ...variables, page: data.itemsPage.page + 1 }
      : null,
  },
  store,
  read,
}
```

Options: `maxPages` caps a run (default 1000); `when` is checked before each run, so app state can decide what deserves to be cached:

```ts
prefetch: {
  next: …,
  when: () => useSettings().cacheCatalog && !navigator.connection?.saveData,
}
```

One run per document at a time; it stops when the app goes offline or a request fails. A page that carries no row a queued mutation has changed is written straight through, so pending work does not slow a prefetch down. `useSync().prefetching` counts the runs in progress, handy for a "caching for offline…" notice.

### Features that shouldn't work offline

The opposite case, a search that must always hit the server (an invoice lookup, say), needs no module option: leave the query without a handler. It is served from the network while online; offline, `data` stays `null` and `error` says why, so gate the UI on `useSync().online`.

```vue
<script setup lang="ts">
const { online } = useSync()
</script>

<template>
  <InvoiceSearch v-if="online" />
  <p v-else>Invoice search needs a connection.</p>
</template>
```

## Mutations against tables

Mutation handlers get the same `db` and write to it directly. Every query whose `read` touches the row follows:

```ts [app/airplane/sites.ts]
export default defineMutationHandlers({
  RenameSite: {
    // GetSites and GetSite both update
    apply: ({ db, variables }) => db.Site.update(variables.id, { name: variables.name }),
  },
  DeleteSite: {
    // Leaves every list that showed it
    apply: ({ db, variables }) => db.Site.delete(variables.id),
  },
  RemoveSiteItem: {
    // Nested data is plain data on the row
    apply: ({ db, variables }) => db.Site.update(variables.siteId, (site) => {
      site.items = site.items.filter(item => item.id !== variables.itemId)
    }),
  },
})
```

Shared helpers can import the module's types from `#nuxt-airplane` (for example `AirplaneDexie`, the typed Dexie instance).

Rollback keeps working without a `revert` handler: for every row `apply` changes, in any table, the server's version is kept and put back. See [Mutation handlers](/guide/mutation-handlers#how-rollback-works).

## Two layers

The tables show what the user should see: what the server said, with the queued mutations applied on top. For every row the queue has changed, the module also keeps the server's version, in a `base` table of its own. Nothing else is recorded about a mutation's effect. Taking the queue off the tables is putting those rows back, and putting it on again is running the `apply` handlers in order.

That is what makes the hard cases simple:

- **A response arrives while changes are pending.** Where it carries a row the queue has changed, that row becomes the new server version and the queue is put on again, so the pending change shows on top of fresh data. A response that touches no such row, a page of a catalog nobody is editing, is written straight through at no extra cost.
- **A mutation is rolled back.** Its rows go back to the server's version. Only if another queued mutation changed the same rows is the queue taken off and put back without it.
- **The server accepts a mutation.** Its rows as they stand are the server's version now, and their `base` entries go.
- **Your own code writes to a table**, outside any mutation, or a `reconcile` does. If the row has a server version set aside, the same fields are changed there, so the write survives the queue coming off.

`apply` always runs on the server's data plus the mutations before it, never on its own earlier effect, so an increment is as safe as a set. A handler that throws when it is applied again does not hold anything up: its change is dropped from view until it syncs. A queued mutation that found nothing to change yet, because its row was not stored, is tried again on each response.

## Room

A cache that only grows meets the browser's storage allowance sooner or later, and a catalog gets there fast. Each fetch record lists the rows its `store` wrote, which lets the module drop the least recently fetched ones, rows and record together:

- when storage use passes 90 % of the allowance, checked after a response is stored;
- when the browser refuses a write for lack of room (`QuotaExceededError`). Room is made and the write is tried once more, whether it was a response or a mutation being queued.

Each time, the oldest quarter of the fetch records goes. What is never dropped:

- a row a queued mutation has changed,
- a row a record that is being kept also lists,
- the records of the queries mounted right now,
- anything your own code wrote outside a `store` handler.

A query whose record was dropped is simply not cached any more: `useQuery` shows it as loading and fetches it again. `useAirplane().evict()` runs the same step on demand and resolves with the number of rows dropped.

Large writes are split up too: a `bulkPut` of thousands of rows goes to IndexedDB 500 at a time inside the same transaction, so the browser gets a turn in between. The handlers themselves run off the main thread, in a [worker](/getting-started/configuration#handlersworker).

## Cache busting

Local data outlives deploys, so a release that changes what a query returns or how a table is shaped needs a way to start over. The module keeps a **cache key** in the database: the [`database.cacheKey`](/getting-started/configuration#databasecachekey) option (a git SHA, a build id) plus a hash of the compiled GraphQL documents. On startup, if the stored key differs from the current one, every table except the outbox is emptied, along with the fetch records, and the key is updated. Fetches and mutations wait for that check, so nothing is written under a stale key.

The **outbox is kept**: changes a user made offline before the redeploy still sync, and are re-applied on top of the fresh data as it arrives. If a release makes old pending mutations invalid, that is the moment to also bump the Dexie store `version` or let them fail and be rolled back.

To wipe programmatically, for example on sign-out, use `useAirplane()`: `clearCache()` empties the tables and keeps the outbox; `clear()` empties everything.

## When to use which

| | `store` + `read` | `read` only | `store` only | No handler |
| --- | --- | --- | --- | --- |
| Works offline | Yes | Yes, from rows other queries stored | No | No |
| Follows local edits | Yes | Yes | No | No |
| Filtering, sorting, search offline | Any, from the tables | Any, from the tables | – | – |
| Use for | Most queries | A detail view over a stored list | Filling a table for other queries | A lookup that must hit the server |
