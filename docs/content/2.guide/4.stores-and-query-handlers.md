By default every query response is cached as one blob keyed by document and variables. That is simple, but the same entity then lives in as many places as there are queries returning it, and a mutation handler has to patch each of them.

Opting a query into your own tables turns that around: you decide how a response is **stored** and how the query is **read** back. A mutation becomes one write to one table, and every query reading that table updates on its own.

## Declare tables

```ts [app/airplane/stores.ts]
export interface SiteRow { id: string, name: string, archived: boolean }
export interface SiteItemRow { siteId: string, itemId: string, onHand: number }

// Types `db.sites` and `db.siteItems` inside handlers
declare global {
  interface NuxtAirplaneStores {
    sites: SiteRow
    siteItems: SiteItemRow
  }
}

export default defineAirplaneStores({
  sites: '&id, name, archived',
  siteItems: '[siteId+itemId], siteId, itemId',
})
```

The argument is Dexie's [`stores()` syntax](https://dexie.org/docs/Version/Version.stores()). The tables are added to the module's own database next to its `queries` and `mutations` tables.

::note
Adding a table or an index needs no version bump: Dexie 4 reconciles the schema on open. Pass `{ version: 2 }` as the second argument when you change an existing table's primary key or want an explicit migration. If the stored database cannot be opened with the declared schema (for example after lowering the version), the module logs a warning and recreates it.
::

## Store and read

```ts [app/airplane/queries.ts]
export default defineQueryHandlers({
  GetSites: {
    // Called with every fresh response. Runs in a transaction.
    async store({ db }, data) {
      await db.sites.clear()
      await db.siteItems.clear()
      await db.sites.bulkPut(data.sites.map(({ id, name, archived }) => ({ id, name, archived })))
      await db.siteItems.bulkPut(data.sites.flatMap(site =>
        site.items.map(item => ({ siteId: site.id, itemId: item.id, onHand: item.onHand }))))
    },
    // Builds the result from the tables. Runs inside liveQuery, so it's reactive.
    async read({ db }) {
      const [sites, siteItems] = await Promise.all([db.sites.toArray(), db.siteItems.toArray()])
      return {
        sites: sites.map(site => ({
          ...site,
          items: siteItems.filter(si => si.siteId === site.id).map(si => ({ id: si.itemId, onHand: si.onHand })),
        })),
      }
    },
  },
  GetSite: {
    store: ({ db }, data) => data.site && db.sites.put(data.site),
    read: async ({ db, variables }) => ({ site: (await db.sites.get(variables.id)) ?? null }),
  },
})
```

Both hooks receive `{ db, variables }`. `read` must return the query's result type, so `useQuery('GetSites')` keeps the same `data` type whether or not the query has a handler.

With a `read` handler the module no longer stores the response blob; it keeps only a metadata row (so `updatedAt` and `loading` still work) and `useQuery` observes `read` instead.

## Mutations against tables

Mutation handlers get the same `db` and write to it directly:

```ts [app/airplane/sites.ts]
export default defineMutationHandlers({
  RenameSite: {
    // GetSites and GetSite both update
    apply: ({ db, variables }) => db.sites.update(variables.id, { name: variables.name }),
  },
  RemoveSiteItem: {
    apply: ({ db, variables }) => db.siteItems.delete([variables.siteId, variables.itemId]),
  },
})
```

Shared helpers can import the module's types from `#nuxt-airplane` (for example `AirplaneDexie`, the typed Dexie instance).

Rollback keeps working without a `revert` handler: every write made during `apply`, to any table, is recorded by an undo log. See [Mutation handlers](/guide/mutation-handlers#how-rollback-works).

## Rebase on refetch

A fresh response replaces whatever `store` writes, which would wipe local changes that haven't reached the server yet. So after every successful fetch the module re-applies the pending mutations, oldest first, on top of the new data. Keep `apply` idempotent with respect to its own result (set a value rather than increment it) and this is invisible.

## Mixing modes

Handlers are per query. A large list can live in tables while a one-off query stays a cached blob, and `cache.update()` in a mutation handler still works for the latter.

## When to use which

| | Cached blob (default) | Your tables |
| --- | --- | --- |
| Setup | None | Stores + `store`/`read` per query |
| One entity in several queries | Patch each query in `apply` | One write |
| Filtering, sorting, search offline | Only what's in the response | Dexie indexes and queries |
| Large lists | Whole blob rewritten per change | Row-level writes |
