Every response object that has an `id` is stored in a table named after its type, and a query is read back from those tables. The same site then lives in one row whether three queries return it or one, a mutation handler updates that row once, and every query showing it re-renders. Nothing has to be declared for this: the tables and their row types come from your schema and documents.

## Inferred tables

At build time the module looks at every selection in your documents. A type that is selected with its `id` field gets a table keyed on it, so with

```graphql
query GetSites { sites { id name archived items { id name onHand } } }
```

`db.Site` and `db.SiteItem` exist in every handler, typed as `Table<SiteRow>` and `Table<SiteItemRow>`. The row type is the union of the fields your documents select on that type: fields selected in every selection are required, the others optional, since a row fetched by one query may lack a field only another query asks for. A nested entity is stored as a reference:

```ts
type SiteRow = { __typename: 'Site', id: string, name: string, archived?: boolean, items?: Array<EntityRef<'SiteItem'>> }
type EntityRef<T> = { __typename: T, id: string }
```

The module adds `__typename` to every selection when it compiles the documents, so a response object always says which table it belongs to. The generated result types leave it optional, so a `read` handler need not produce it.

When a response arrives, each entity is upserted into its table, merging into what the table already holds, and the response is stored as a skeleton of references under the query's key. Reading the query puts the rows back, inside a live query, so it stays current:

- `db.Site.update(id, { name })` in a mutation handler shows up in every query listing that site.
- `db.Site.delete(id)` drops the site from every list and makes a single-site query return `null`.
- A new row still has to be put where a query will find it: add it to the query's result with [`cache.update()`](/guide/mutation-handlers#cache) or write a [`read`](#custom-read) that lists the table.

Object types without an `id` (a connection, a page, a nested value object) stay embedded where they were.

::note
A filter the server has never seen, such as a search typed while offline, returns nothing by default: the skeleton only knows the variable sets that were fetched. A [custom `read`](#custom-read) over the tables lifts that limit.
::

## Extra indexes and your own tables

`defineAirplaneStores` adds to what is inferred. For an entity table, list the indexes a `read` handler sorts or filters on; the key is implied. Any other name declares a table of your own, in Dexie's [`stores()` syntax](https://dexie.org/docs/Version/Version.stores()).

```ts [app/airplane/stores.ts]
export default defineAirplaneStores({
  Item: 'name',
  drafts: '++id, siteId',
})
```

Your own tables are typed by augmenting `NuxtAirplaneStores`:

```ts
declare global {
  interface NuxtAirplaneStores {
    drafts: { id?: number, siteId: string, body: string }
  }
}
```

::note
Adding a table or an index needs no version bump: Dexie 4 reconciles the schema on open. Pass `{ version: 2 }` as the second argument when you change an existing table's primary key or want an explicit migration. If the stored database cannot be opened with the declared schema (for example after lowering the version), the module logs a warning and recreates it.
::

::tip
IndexedDB cannot use booleans as index keys, so an index on `archived` matches nothing; filter booleans in JavaScript, or store flags you want to index as `0 | 1` in a table of your own. In development the module warns in the console the first time a boolean is written to an indexed key.
::

## Custom read

A `read` handler builds the query's result from the tables instead of from the stored skeleton. The rows are still written for it. Use it when a query should answer variables it has never sent, or shape the data differently from the response:

```ts [app/airplane/queries/get-sites.ts]
export default defineQueryHandler('GetSites', {
  async read({ db, variables }) {
    const { archived, search } = variables ?? {}
    const q = search?.trim().toLowerCase()
    const sites = (await db.Site.toArray())
      .filter(s => archived == null || s.archived === archived)
      .filter(s => !q || s.name.toLowerCase().includes(q))
    return {
      sites: await Promise.all(sites.map(async site => ({
        ...site,
        archived: site.archived ?? false,
        items: (await db.SiteItem.bulkGet((site.items ?? []).map(ref => ref.id))).filter(i => i !== undefined),
      }))),
    }
  },
})
```

`read` runs inside Dexie's `liveQuery`, so whatever it reads is observed. It must return the query's result type, so `useQuery('GetSites')` keeps the same `data` type with or without a handler. With a `read` handler the module keeps only a metadata row for the query (so `updatedAt` and `loading` still work) and `useQuery` observes `read` instead.

## Custom store

A `store` handler takes over writing a response: nothing is normalized for that query and the response is kept as a blob. Pair it with `read` to keep data in tables of your own shape, for example a join table keyed on two ids:

```ts [app/airplane/queries.ts]
export default defineQueryHandlers({
  GetSites: {
    async store({ db }, data) {
      await db.sites.bulkPut(data.sites.map(({ id, name, archived }) => ({ id, name, archived: archived ? 1 : 0 })))
      await db.siteItems.bulkPut(data.sites.flatMap(site =>
        site.items.map(item => ({ siteId: site.id, itemId: item.id, onHand: item.onHand }))))
    },
    async read({ db }) {
      const [sites, siteItems] = await Promise.all([db.sites.toArray(), db.siteItems.toArray()])
      return {
        sites: sites.map(site => ({
          ...site,
          archived: site.archived === 1,
          items: siteItems.filter(si => si.siteId === site.id).map(si => ({ id: si.itemId, name: '', onHand: si.onHand })),
        })),
      }
    },
  },
})
```

`store` runs in a transaction over every table. Both hooks receive `{ db, variables }`.

## Variables

Both hooks receive the query's `variables`, so a filtered query is a local filter in `read`, as in the example above, and a scoped write in a custom `store`. Each set of variables is its own request and its own `updatedAt`, but they all read the same tables, so a filter the server has never seen still works offline against what is cached. The flip side: a filtered response cannot tell you about deletions outside its scope, so keep one broad fetch around (an unfiltered query, or `refetch: ['GetSites']` after sync) to reconcile.

Rows are never deleted by a response, only upserted. A row that disappeared on the server stays in its table until a mutation handler deletes it or the cache is cleared; it only leaves the queries whose fresh skeleton no longer references it.

## Pagination

A Relay-style connection fits the same pattern. The nodes land in their table on their own, and `read` rebuilds the page from it using the same cursor logic as the server. If cursors are derived from the row itself (for example a base64 of the sort key and id) rather than from a server-side offset, the local read paginates identically, and a user can keep paging offline through whatever has been fetched.

```ts
SearchItems: {
  async read({ db, variables }) {
    const { query, first = 20, after } = variables
    const all = (await db.Item.orderBy('name').toArray()).filter(i => !query || i.name.includes(query))
    const start = after ? all.findIndex(i => cursorOf(i) === after) + 1 : 0
    const page = all.slice(start, start + first)
    return {
      searchItems: {
        edges: page.map(node => ({ cursor: cursorOf(node), node })),
        totalCount: all.length,
        pageInfo: { hasNextPage: start + first < all.length, endCursor: page.length ? cursorOf(page.at(-1)!) : null },
      },
    }
  },
}
```

In the UI, give each page its own `useQuery` (a small component per page works well) and push the previous page's `endCursor` to load the next one. `hasNextPage` and `totalCount` reflect local data while offline, so they can differ from the server's until you're back online.

Classic numbered pages work the same way with `page` / `pageSize` variables: `read` slices the sorted local rows at `(page - 1) * pageSize`, and a single `useQuery` whose `page` variable changes gives every visited page its own cached row. Offset pages are only accurate offline for pages that were fetched; an unvisited page shows whatever local data sits at that offset.

## Prefetching every page

A paginated query only caches the pages a user visits. Opt it into `prefetch` and, after any page is fetched, the module keeps requesting the next one in the background until there are none left, storing each page (and its metadata, so every page counts as cached). The whole set is then available offline.

`next` receives the page just fetched and its variables and returns the next page's variables, or `null` at the end. That covers Relay connections and numbered pages alike:

```ts
// Relay: follow the end cursor
SearchItems: {
  prefetch: {
    next: (data, variables) => data.searchItems.pageInfo.hasNextPage
      ? { ...variables, after: data.searchItems.pageInfo.endCursor }
      : null,
  },
  read,
}

// Numbered pages: page + 1 until the last
ItemsPage: {
  prefetch: {
    next: (data, variables) => data.itemsPage.page < data.itemsPage.totalPages
      ? { ...variables, page: data.itemsPage.page + 1 }
      : null,
  },
  read,
}
```

Options: `maxPages` caps a run (default 1000); `when` is checked before each run, so app state can decide what deserves to be cached:

```ts
prefetch: {
  next: …,
  when: () => useSettings().cacheCatalog && !navigator.connection?.saveData,
}
```

One run per document at a time; it stops when the app goes offline or a request fails, and pending mutations are re-applied once at the end. `useSync().prefetching` counts the runs in progress, handy for a "caching for offline…" notice.

### Features that shouldn't work offline

The opposite case, a search that must always hit the server (an invoice lookup, say), needs no module option: leave the query without a handler and don't prefetch it, then gate the UI on `useSync().online`.

```vue
<script setup lang="ts">
const { online } = useSync()
</script>

<template>
  <InvoiceSearch v-if="online" />
  <p v-else>Invoice search needs a connection.</p>
</template>
```

## Mutations against tables

Mutation handlers get the same `db` and write to it directly:

```ts [app/airplane/sites.ts]
export default defineMutationHandlers({
  RenameSite: {
    // GetSites and GetSite both update
    apply: ({ db, variables }) => db.Site.update(variables.id, { name: variables.name }),
  },
  DeleteSite: {
    // Leaves every list that showed it
    apply: ({ db, variables }) => db.Site.delete(variables.id),
  },
  RemoveSiteItem: {
    // References are plain data on the row
    apply: ({ db, variables }) => db.Site.update(variables.siteId, (site) => {
      site.items = (site.items ?? []).filter(ref => ref.id !== variables.itemId)
    }),
  },
})
```

Shared helpers can import the module's types from `#nuxt-airplane` (for example `AirplaneDexie`, the typed Dexie instance).

Rollback keeps working without a `revert` handler: every write made during `apply`, to any table, is recorded by an undo log. See [Mutation handlers](/guide/mutation-handlers#how-rollback-works).

## Rebase on refetch

A fresh response overwrites the fields it carries, which would wipe local changes that haven't reached the server yet. So after every successful fetch the module re-applies the pending mutations, oldest first, on top of the new data. Keep `apply` idempotent with respect to its own result (set a value rather than increment it) and this is invisible.

## Mixing modes

Handlers are per query. Most queries need none; a query that must filter offline gets a `read`; one with its own storage gets `store` and `read`. `cache.update()` in a mutation handler works for all of them: it hands the handler the query's data as `useQuery` would see it, and splits what the handler writes back into the tables.

With [`normalize: false`](/getting-started/configuration#normalize) every query without a `store` handler is cached as one blob instead, and `cache.update()` patches that blob.

## Cache busting

Local data outlives deploys, so a release that changes what a query returns or how a table is shaped needs a way to start over. The module keeps a **cache key** in the database: the [`cacheKey`](/getting-started/configuration#cachekey) option (a git SHA, a build id) plus a hash of the compiled GraphQL documents. On startup, if the stored key differs from the current one, the `queries` table and every store you declared are emptied and the key is updated. Fetches and mutations wait for that check, so nothing is written under a stale key.

The **outbox is kept**: changes a user made offline before the redeploy still sync, and are re-applied on top of the fresh data as it arrives. If a release makes old pending mutations invalid, that is the moment to also bump the Dexie store `version` or let them fail and be rolled back.

To wipe programmatically, for example on sign-out, use `useAirplane()`: `clearCache()` empties cached data and keeps the outbox; `clear()` empties everything.

## When to use which

| | Inferred tables (default) | Plus a custom `read` | Your own `store` and `read` | Cached blob (`normalize: false`) |
| --- | --- | --- | --- | --- |
| Setup | None | One function | Stores + two functions | None |
| One entity in several queries | One write | One write | One write | Patch each query in `apply` |
| Filtering, sorting, search offline | Fetched variables only | Any, from the tables | Any, from the tables | Fetched variables only |
| Row shape | What the documents select | Same | Yours | The response |
