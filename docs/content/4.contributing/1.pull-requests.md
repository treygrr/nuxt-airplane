Thanks for considering a contribution. This page is the whole process, from idea to release. The short version: open an issue for anything non-trivial, keep PRs focused, cover behaviour with tests, update the docs and playground when behaviour changes, and make sure the checks pass.

## Before you start

- **Bugs**: open an issue with a minimal reproduction (a `.gql` document, a handler and the steps), or a failing test. A PR with just a failing test is welcome.
- **Features and behaviour changes**: open an issue first and describe the problem you are solving, not only the solution. The module has a small, opinionated surface; agreeing on the shape before you write code avoids wasted work on both sides.
- **Docs fixes, typos, small refactors**: just open the PR.

Check the existing issues and PRs first; a duplicate is better closed early than after review.

## Setting up

```bash
git clone https://github.com/treygrr/nuxt-airplane
cd nuxt-airplane
npm install            # installs the module, playground and docs workspaces
npm run dev            # playground at http://localhost:3000, with an in-memory Apollo server
npm run docs:dev       # docs site
```

The playground is where behaviour is exercised: it has a protected GraphQL endpoint, normalized tables, cursor and numbered pagination, a pending-changes list with rollback, and a *Go offline* switch. If your change affects what users see, make it visible there.

## Scope of a PR

One concern per PR. A bug fix, a feature, or a refactor, not two of them together. If a feature needs a refactor first, send the refactor as its own PR; it is easier to review and can land independently.

Keep the diff to what the change needs. Drive-by formatting, renames or reorganisation in unrelated files make the review harder and the history noisier. If you spot something worth cleaning up, mention it or open a separate PR.

## What a PR needs

::steps{level="3"}

### Tests

Every behaviour change comes with tests. There are three layers; pick the lowest one that can express the behaviour:

| Layer | File | Runs against |
| --- | --- | --- |
| Runtime client | `test/client.test.ts` | Real Dexie on `fake-indexeddb`, mocked `fetch` acting as the server |
| Build-time (codegen) | `test/codegen.test.ts` | Temp directories and stubbed `fetch` |
| Module in a Nuxt app | `test/basic.test.ts` + `test/fixtures/basic` | A real Nuxt build via `@nuxt/test-utils` |

A bug fix should include a test that fails without the fix. For sync, rollback or rebase changes, prefer the client layer: it runs the undo log, the outbox and the transactions for real.

### Docs

The docs live in `docs/content` and are deployed from `main`. Update them in the same PR when you change:

- a composable's signature or return value (`docs/content/3.api/`),
- behaviour described in a guide (`docs/content/2.guide/`),
- a module option (`docs/content/1.getting-started/3.configuration.md` and `3.api/8.module-options.md`).

The README is the npm landing page; keep its examples in sync when the public API moves.

### Playground

If users will see or do something new, add or adjust it in `playground/`. It doubles as the manual test bed reviewers use.

### Checks

Run the same checks CI runs before pushing:

```bash
npm run lint
npm run test          # ~30 s, includes the Nuxt e2e build
npm run test:types    # module and playground
cd docs && npm run lint
```

### Commit messages

Releases are cut with `changelogen`, which builds the changelog from commit messages, so use [Conventional Commits](https://www.conventionalcommits.org):

```
feat(client): prefetch every page of a paginated query
fix(sync): re-queue rows left in syncing by a closed tab
docs: add protected-API recipe to the auth guide
```

Use `feat` and `fix` for anything user-facing, `docs`, `test`, `refactor`, `chore` otherwise. A breaking change gets `!` after the type and a `BREAKING CHANGE:` footer explaining the migration. One logical change per commit is nice to have; squashing on merge is fine too.

### The title

The title is checked by CI and becomes the squash-merge commit, so it follows the same convention: `type(scope): subject`, lower-case subject, no trailing period, under about 70 characters. Scopes are optional; the ones in use are `client`, `sync`, `codegen`, `module`, `playground`, `docs`.

| Good | Why |
| --- | --- |
| `feat(client): prefetch every page of a paginated query` | New capability, says what it does |
| `feat: add defineAirplaneRequest for auth headers` | Scope optional when the change spans areas |
| `fix(sync): re-queue rows left in syncing by a closed tab` | Names the bug, not the symptom's ticket number |
| `fix(codegen): resolve relative schema path against rootDir` | |
| `perf(client): batch undo-log writes in one transaction` | |
| `refactor(module): split handler scanning out of setup` | No behaviour change |
| `docs: add protected-API recipe to the auth guide` | |
| `docs(api): document the timeout option` | |
| `test(client): cover rollback with a revert hook` | |
| `chore(deps): bump dexie to 4.5` | What Dependabot produces |
| `ci: fail the package job on unexpected tarball files` | |
| `feat(client)!: store boolean flags as 0/1 in stores` | `!` marks a breaking change; explain the migration in the body |

| Avoid | Problem |
| --- | --- |
| `Fix bug` | No type prefix, says nothing |
| `feat: Added prefetch support.` | Capitalised subject and trailing period; the changelog quotes it verbatim |
| `fix: #42` | Reference the issue in the body (`Closes #42`), describe the fix in the title |
| `fix(sync): re-queue stuck rows and add timeout and update docs` | Three changes; split the PR |
| `WIP: rollback rework` | Open it as a draft PR instead |
| `update client.ts` | Describes the diff, not the change |

### The description

The PR template asks for:

- **What** changed and **why**, in a few sentences. Link the issue.
- **How to verify**: steps in the playground, or which tests cover it.
- Anything a reviewer should know: trade-offs, follow-ups you left out on purpose, areas you are unsure about.

::

## Design principles to keep in mind

These are the constraints the module is built around; a PR that bends one of them needs a good reason in the description.

- **Operations are static.** Documents come from `.gql` files at build time; nothing builds GraphQL from strings at runtime.
- **The cache is the source of truth for the UI.** `useQuery` reads IndexedDB; the network only updates the cache.
- **Mutations are never lost silently.** Rejected ones are parked as `failed`, the outbox survives cache busts, and the only destructive path (an unopenable schema) is logged.
- **Credentials are computed, never persisted.** Headers are produced at send time by `defineAirplaneRequest`.
- **Opt-in complexity.** Blob caching works with zero handlers; stores, query handlers, prefetch and per-file layouts are layers users choose.
- **Nothing is rendered by the module.** It provides data and state; UI belongs to the app.

## What runs when you open a PR

GitHub Actions does the mechanical part of the review so humans can focus on the design:

| Check | What it does | Fails the PR? |
| --- | --- | --- |
| `ci` | Lint, the full test suite, module and playground type checks | Yes |
| `pr / Conventional title` | The PR title must be a Conventional Commit; it becomes the squash-merge message and a changelog line | Yes |
| `pr / Label by area` | Adds `module`, `docs`, `playground`, `tests`, `ci`, `dependencies` labels from the paths you touched | No |
| `pr / Dependency review` | Flags newly added dependencies with known high-severity vulnerabilities | Yes |
| `pr / Package` | Builds the npm tarball as `npm publish` would, posts its contents and size in the job summary, fails if anything outside `dist/`, README, LICENSE sneaks in, and uploads it as an artifact | Yes (when `src/` changed) |
| `pr / Preview package` | Publishes an installable preview to [pkg.pr.new](https://pkg.pr.new) and comments the install command | No |
| `pr / Docs build` | Builds the docs site with the Pages preset and uploads it as an artifact | Yes (when `docs/` changed) |
| `pr / Playground build` | Production build of the playground | Yes (when `src/` or `playground/` changed) |
| `codeql` | Static analysis; findings appear in the Security tab | Yes |

A first PR also gets a short welcome comment pointing here. A PR with no activity for 30 days is labelled `stale` and closed two weeks later; reopen it whenever you pick it up again (`pinned` or `work-in-progress` labels exempt it).

## Review

A maintainer will review within a few days. Expect questions about edge cases around offline, rollback and rebase; those are where bugs hide. Please respond to review comments by pushing new commits rather than force-pushing over the history, so the conversation stays attached to the code.

PRs are merged when:

- CI is green (lint, tests, type checks),
- the change has tests and, where relevant, docs and playground updates,
- a maintainer has approved.

Stale PRs with unanswered review comments are closed after a month; feel free to reopen when you pick it up again.

## Releases

Maintainers release from `main` with `npm run release`, which lints, tests, builds, bumps the version and changelog from the commit history, publishes to npm and pushes the tag. Contributors don't need to touch versions or the changelog.

## Security issues

Don't open a public issue or PR for a vulnerability. Use a private security advisory on the GitHub repository; see the [Security guide](/guide/security).
