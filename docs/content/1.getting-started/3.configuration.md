All options sit under the `airplane` key of `nuxt.config.ts`.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-airplane'],
  airplane: {
    endpoint: '/api/graphql',
    schema: './schema.graphql',
    documents: ['**/*.gql', '**/*.graphql'],
    handlersDir: 'airplane',
    dbName: 'nuxt-airplane',
    headers: {},
    schemaHeaders: {},
    codegen: {}
  }
})
```

## Options

### `endpoint`

- Default: `'/api/graphql'`

URL the client posts operations to. A relative path is resolved against the app's own origin, which is handy when the GraphQL server is a Nitro route in the same project.

### `schema`

- Default: `undefined`

Where the schema used for type generation comes from. Either a path to an SDL file (relative paths resolve against the project root) or a URL to introspect. When omitted the module introspects `endpoint`.

::note
In dev a relative `endpoint` can only be introspected once the dev server is up, so the first type generation is untyped and a second one runs a moment after "Ready". The last successfully loaded schema is cached in `node_modules/.cache/nuxt-airplane/schema.graphql` and used as a fallback, so a production build without a running server still gets types.
::

### `headers`

- Default: `{}`

Static headers sent with every request. Public runtime config, so only for values you would expose anyway (an API key, a client id). Per-user tokens belong in [`defineAirplaneRequest`](/guide/auth-and-headers), whose headers are merged on top of these.

### `schemaHeaders`

- Default: `{}`

Headers for the build-time introspection request when the endpoint is protected, e.g. `{ Authorization: \`Bearer ${process.env.INTROSPECTION_TOKEN}\` }`. Read on the server during the build, never shipped.

### `documents`

- Default: `['**/*.gql', '**/*.graphql']`

Globs, relative to `srcDir`, of the files holding your operations. Files are watched in dev and the composables regenerate on change.

### `handlersDir`

- Default: `'airplane'`

Directory, relative to `srcDir`, scanned for handler files: `defineMutationHandler(s)`, `defineQueryHandler(s)` and `defineAirplaneStores` default exports. Every `.ts` / `.js` file in it (at any depth) is imported, except that a folder containing an `index` file is one unit: only the index is imported, so it can compose the files beside it. See [Organizing handler files](/guide/mutation-handlers#organizing-handler-files).

### `dbName`

- Default: `'nuxt-airplane'`

Name of the IndexedDB database. Change it if several apps on the same origin use the module.

### `cacheKey`

- Default: `undefined`

A deploy-specific string. The module stores the key its data was written under; when it differs on the next load, the cached data (the `queries` table and your stores) is wiped and refetched, while the outbox of pending mutations is kept. A hash of the compiled GraphQL documents is always mixed in, so editing a query busts the cache even if you forget to change this.

```ts [nuxt.config.ts]
airplane: {
  cacheKey: process.env.GIT_SHA ?? process.env.VERCEL_GIT_COMMIT_SHA,
}
```

It is runtime config, so `NUXT_PUBLIC_AIRPLANE_CACHE_KEY` overrides it at deploy time without a rebuild. See [Cache busting](/guide/stores-and-query-handlers#cache-busting).

### `codegen`

- Default: `{}`

Extra configuration passed to the `typescript` and `typescript-operations` plugins of GraphQL Code Generator. The module sets `namingConvention: 'keep'` and types the `ID` scalar as `string`; anything you pass here is merged on top.

```ts
airplane: {
  codegen: {
    scalars: { DateTime: 'string' },
    avoidOptionals: true
  }
}
```

## Runtime config

`endpoint`, `dbName` and `cacheKey` are exposed as `runtimeConfig.public.airplane`, so they can be overridden with `NUXT_PUBLIC_AIRPLANE_ENDPOINT` and `NUXT_PUBLIC_AIRPLANE_CACHE_KEY` at runtime.
