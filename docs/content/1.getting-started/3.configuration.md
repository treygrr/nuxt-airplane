All options sit under the `airplane` key of `nuxt.config.ts`.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@treygrr/nuxt-airplane'],
  airplane: {
    endpoint: '/api/graphql',
    headers: {},
    persistedQueries: false,
    documents: ['**/*.gql', '**/*.graphql'],
    schema: {
      source: './schema.graphql',
      headers: {},
    },
    handlers: {
      dir: 'airplane',
      worker: true,
      generate: false,
    },
    database: {
      name: 'nuxt-airplane',
      cacheKey: undefined,
      schemaFile: undefined,
    },
    codegen: {},
  },
})
```

Options that belong together are grouped: `schema` for where the types come from, `handlers` for the handler files, `database` for the local database. A group is merged with its defaults, so you only write the keys you change. An option written under a name from before the grouping, such as `handlersDir` or `cacheKey` at the top level, stops the build with a message that says where it went.

## Options

### `endpoint`

- Default: `'/api/graphql'`

URL the client posts operations to. A relative path is resolved against the app's own origin, which is handy when the GraphQL server is a Nitro route in the same project.

### `headers`

- Default: `{}`

Static headers sent with every request. Public runtime config, so only for values you would expose anyway (an API key, a client id). Per-user tokens belong in [`defineAirplaneRequest`](/guide/auth-and-headers), whose headers are merged on top of these.

### `startOffline`

- Default: `false`

Start the app held offline, as if `goOffline()` had been called, until the user chooses otherwise. Their `goOffline()` / `goOnline()` is [kept](/guide/sync-and-offline#the-choice-is-kept) and wins from then on. It is runtime config, so `NUXT_PUBLIC_AIRPLANE_START_OFFLINE` sets it at deploy time.

### `persistedQueries`

- Default: `false`

Send operations as a SHA-256 hash of their text instead of the text itself. Requests get smaller, and in `'manifest'` mode the server can reject anything that is not one of your build's documents.

- `'automatic'`: [automatic persisted queries](https://www.apollographql.com/docs/apollo-server/performance/apq) as Apollo Server, GraphQL Yoga (with its APQ plugin), Hive and others implement them. The hash goes first; when the server answers `PersistedQueryNotFound` the text is sent along with it, once, and the hash alone works from then on. A server that answers `PersistedQueryNotSupported` gets full documents for the rest of the session, so enabling this against a server without support costs one extra round trip.
- `'manifest'`: only the hash is ever sent. Register the documents on the server first from the manifest the module writes to `.nuxt/nuxt-airplane/persisted-queries.json` at build time (Apollo's persisted query manifest format: `{ format, version, operations: [{ id, name, type, body }] }`). An unknown hash is a GraphQL error like any other.

The hash is computed at build time from the exact text that is sent, fragments included, so it matches whatever the server computes from the body of an automatic registration or from the manifest.

```ts [nuxt.config.ts]
airplane: {
  persistedQueries: 'automatic',
}
```

### `documents`

- Default: `['**/*.gql', '**/*.graphql']`

Globs, relative to `srcDir`, of the files holding your operations. Files are watched in dev and the composables regenerate on change.

### `schema`

Where the GraphQL schema comes from. Types are generated from it at build time.

#### `schema.source`

- Default: `undefined`

Where the schema used for type generation comes from. Either a path to an SDL file (relative paths resolve against the project root) or a URL to introspect. When omitted the module introspects `endpoint`.

```ts [nuxt.config.ts]
airplane: {
  schema: { source: './schema.graphql' },
}
```

::note
In dev a relative `endpoint` can only be introspected once the dev server is up, so the first type generation is untyped and a second one runs a moment after "Ready". The last successfully loaded schema is cached in `node_modules/.cache/nuxt-airplane/schema.graphql` and used as a fallback, so a production build without a running server still gets types.
::

#### `schema.headers`

- Default: `{}`

Headers for the build-time introspection request when the endpoint is protected, e.g. `{ Authorization: \`Bearer ${process.env.INTROSPECTION_TOKEN}\` }`. Read on the server during the build, never shipped.

### `handlers`

The files that say what each operation means for the local data: where they are, where they run, and whether to scaffold them.

#### `handlers.dir`

- Default: `'airplane'`

Directory, relative to `srcDir`, scanned for handler files: `defineMutationHandler(s)`, `defineQueryHandler(s)` and `defineAirplaneStores` default exports. Every `.ts` / `.js` file in it (at any depth) is imported, except that a folder containing an `index` file is one unit: only the index is imported, so it can compose the files beside it. See [Organizing handler files](/guide/mutation-handlers#organizing-handler-files). With [`handlers.generate`](#handlersgenerate) this is also where the scaffolded files are written.

#### `handlers.worker`

- Default: `true`

The handlers that write to the tables run in a [web worker](https://developer.mozilla.org/docs/Web/API/Web_Workers_API). Storing a large response, applying a mutation, and putting the queue back on after a refetch happen off the main thread, and the page stays responsive while a catalog is prefetched or a long queue syncs.

The page still talks to the network and reads the tables. It asks the worker for every write, and the live queries pick up what the worker committed, so components need nothing special. What it decides is where your handlers run:

| In the worker | On the page |
| --- | --- |
| `store` | `read` |
| `describe`, `apply`, `merge`, `reconcile`, `revert` | `prefetch.next`, `prefetch.when` |
| | everything in `defineAirplaneRequest` |

A handler that runs in the worker has no Nuxt app, no component state and no DOM: `useRoute()`, `useState()` or `window` do not exist there. It gets `db` and `variables`, and anything it imports, auto-imports included, is bundled into the worker. Variables and responses cross to the worker as plain data, which they already are for GraphQL.

Turn it off to run every handler on the page, for an app whose handlers lean on composables:

```ts [nuxt.config.ts]
airplane: {
  handlers: { worker: false },
}
```

The worker needs the Vite builder; with another builder the handlers stay on the page. So they do in a browser that cannot start the worker, with a warning in the console.

#### `handlers.generate`

- Default: `false`

Write a handler file for every query and mutation that has none, with the hooks in place and their bodies empty. A starting point for a new app, or for the operations you add later.

```ts [nuxt.config.ts]
airplane: {
  handlers: { generate: true },
}
```

Files go under the [handlers directory](#handlersdir), one per operation, named after it: `mutations/rename-site.ts` for `RenameSite`, `queries/get-sites.ts` for `GetSites`. Each starts with the operation's text as a comment, so its variables and selection are in view:

```ts [app/airplane/mutations/rename-site.ts]
// Scaffolded by nuxt-airplane (`handlers.generate`). The file is yours: fill it in, change it, it is never overwritten.
//
//   mutation RenameSite($id: ID!, $name: String!) {
//     renameSite(id: $id, name: $name) { id name }
//   }

export default defineMutationHandler('RenameSite', {
  // Runs as soon as the mutation is queued: change the tables so the UI shows it at once.
  // Receives { db, result, variables, local, tempId }.
  apply() {

  },

  // Runs with the server's answer: write what it assigned (ids, timestamps) into the tables.
  // Receives { db, result, variables, local, tempIds, resolve } and the result.
  reconcile() {

  },
})
```

A query gets `store` and `read` the same way, with a line saying that a result with no `id` can take `store: 'result'` instead. The files are written when the app is prepared, built or started, and in dev as soon as you add an operation to a `.gql` file.

What it will not do:

- **Overwrite anything.** A file that exists is left alone, whatever is in it, and the files it wrote are yours from then on.
- **Duplicate a handler.** An operation that any file in the handlers directory already declares a handler for is skipped, whether with `defineMutationHandler('RenameSite', …)` or as a key of `defineMutationHandlers({ RenameSite: … })`.
- **Scaffold subscriptions**, which have no handlers.

Two things to know before turning it on in an app that already runs:

- A query whose handler has a `read` shows what `read` returns. The scaffolded one returns `null`, so the query shows nothing until you fill it in, where before it showed the network's answer. Delete the `read` hook, or the file, for a query you want to leave on the network.
- A folder with an [`index` file](/guide/mutation-handlers#organizing-handler-files) is imported through its index only. A file scaffolded into such a folder is not picked up until the index exports it, and the module says so in the log.

### `database`

The IndexedDB database that holds the tables and the outbox.

#### `database.name`

- Default: `'nuxt-airplane'`

Name of the IndexedDB database. Change it if several apps on the same origin use the module.

#### `database.cacheKey`

- Default: `undefined`

A deploy-specific string. The module stores the key its data was written under; when it differs on the next load, every table and the fetch records are wiped and the queries refetched, while the outbox of pending mutations is kept. A hash of the compiled GraphQL documents is always mixed in, so editing a query busts the cache even if you forget to change this.

```ts [nuxt.config.ts]
airplane: {
  database: {
    cacheKey: process.env.GIT_SHA ?? process.env.VERCEL_GIT_COMMIT_SHA,
  },
}
```

It is runtime config, so `NUXT_PUBLIC_AIRPLANE_CACHE_KEY` overrides it at deploy time without a rebuild. See [Cache busting](/guide/stores-and-query-handlers#cache-busting).

#### `database.schemaFile`

- Default: `undefined`

A file, relative to `srcDir`, to write the [database schema](/guide/stores-and-query-handlers#the-schema-file) to as well, for example `'airplane.schema.ts'`. Commit it, and a change to the tables shows up in review. It must be outside the handlers directory. Without it the schema is still written, to `.nuxt/nuxt-airplane/schema.ts`.

```ts [nuxt.config.ts]
airplane: {
  database: {
    schemaFile: 'airplane.schema.ts',
  },
}
```

### `codegen`

- Default: `{}`

Extra configuration passed to the `typescript-operations` plugin of GraphQL Code Generator. The module sets `namingConvention: 'keep'` and types the `ID` scalar as `string`; anything you pass here is merged on top, and `scalars` is merged with the `ID` mapping rather than replacing it.

```ts
airplane: {
  codegen: {
    scalars: { DateTime: 'string' },
    enumType: 'native',
  }
}
```

A custom scalar you do not map is `any`, in the operation types and in the [row types](/guide/type-generation#row-types). Enums are string unions (`'PLACED' | 'SHIPPED'`) unless you choose otherwise with `enumType`, so a handler can write a plain string to a row.

`nonOptionalTypename: true` types `__typename` on every object, so the module also asks for it in every selection set it sends; without it the documents are sent as written. See [Type generation](/guide/type-generation#nonoptionaltypename).

### `imports`

- Default: `{}`

The names the composables are auto-imported under. Give one another name when it would clash with another library's, or to suit your own:

```ts
airplane: {
  imports: { useAirplaneQuery: 'useQuery', useOnlineQuery: 'useRemoteQuery' },
}
```

The keys are `useAirplaneQuery`, `useOnlineQuery`, `useMutation`, `useSync` and `useAirplane`; one left out keeps its name. Types follow the new names. An unknown key, a name that is not a valid identifier, or two composables under one name stops the build. The `define*` helpers keep their names: the build finds the handler files by them.

## Runtime config

`endpoint`, `database.name`, `database.cacheKey`, `persistedQueries` and `startOffline` are exposed as `runtimeConfig.public.airplane` (as `endpoint`, `dbName`, `cacheKey`, `persistedQueries` and `startOffline`), so they can be overridden with `NUXT_PUBLIC_AIRPLANE_ENDPOINT`, `NUXT_PUBLIC_AIRPLANE_CACHE_KEY`, `NUXT_PUBLIC_AIRPLANE_PERSISTED_QUERIES` and `NUXT_PUBLIC_AIRPLANE_START_OFFLINE` at runtime (an empty string turns persisted queries off).
