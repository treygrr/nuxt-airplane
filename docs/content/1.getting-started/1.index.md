`nuxt-airplane` is a Nuxt module for apps that must keep working without a connection. You give it a GraphQL endpoint and your `.gql` files; it gives you typed composables whose data comes from a local database rather than from the network.

## Why it exists

Some apps are used where the connection is not: a warehouse aisle, a basement, a delivery route, a plane. The people using them still have to look things up and record what they did, and what they recorded has to reach the server later, once, in the order it happened.

A GraphQL client is built around the request. It caches responses, so a screen that was visited online can be shown again. But a cache of responses answers the questions that were asked: a search or a filter nobody ran online has nothing to show offline. And a change made offline is a patch on that cache, waiting for an answer. Keeping it through a reload, sending it after the change it depends on, trying again when the server was busy, and letting the person who made it take it back tends to be left to the app.

`nuxt-airplane` starts from the other end. The local database is what the app reads and writes, and the network is how it catches up:

- **Queries read tables, not responses.** What was fetched is stored as rows, and a query's result is built from them, so a filter runs against everything on the device, and a local change shows in every query that reads the row.
- **A change is kept until the server has it.** It is applied to the tables at once and queued in the database, where it survives a reload, waits for the changes it depends on, and is retried when the connection or the server lets it down.
- **The person stays in charge.** Every pending change can be listed, retried or rolled back, and the app can be held offline on purpose.

The cost is that you say how each query maps to the tables, in a [handler](/guide/stores-and-query-handlers). The tables and their types come from your documents, so a handler is usually a few lines. If the app is only ever used online, you do not need any of this, and a plain GraphQL client is the simpler choice.

## How it works

::steps{level="3"}

### Operations become composables

Every named operation in your documents is registered under its name. `useAirplaneQuery('GetSites')` and `useMutation('RenameSite')` are typed from the schema, so a typo in the name or in the variables is a compile error.

### Data lives in IndexedDB tables

Every type your documents select with an `id` gets a [table inferred from them](/guide/stores-and-query-handlers), typed from the fields they select and created once your code uses it, in a [Dexie](https://dexie.org) database. A query handler writes a response into the tables with `store` and builds the query's result from them with `read`. `useAirplaneQuery` returns **what `read` returns, live**: stored data renders immediately, a refetch runs in the background when online, and anything that edits a row updates every component reading it.

### Mutations apply locally and queue

`mutate()` runs your `apply` handler against the tables, stores the mutation and its variables in an outbox, and resolves. A sync loop sends the queue to the server in order whenever the app is online.

### Pending changes can be rolled back

Until a mutation has reached the server it can be undone. The rows it touched are restored and any later pending mutations are replayed on top.

::

## What you write

```graphql [app/graphql/sites.gql]
query GetSites {
  sites { id name archived }
}

mutation RenameSite($id: ID!, $name: String!) {
  renameSite(id: $id, name: $name) { id name }
}
```

```ts [app/airplane/sites.ts]
export default defineQueryHandlers({
  GetSites: {
    store: ({ db }, data) => db.Site.bulkPut(data.sites),
    read: async ({ db }) => ({ sites: await db.Site.toArray() }),
  }
})
```

```ts [app/airplane/mutations.ts]
export default defineMutationHandlers({
  RenameSite: {
    apply: ({ db, variables }) => db.Site.update(variables.id, { name: variables.name })
  }
})
```

```vue [app/pages/sites.vue]
<script setup lang="ts">
const { data, loading } = useAirplaneQuery('GetSites')
const rename = useMutation('RenameSite')
const { online, pending } = useSync()
</script>
```

## What you get

- `useAirplaneQuery(name, variables?)` — see [Queries](/guide/queries)
- `useOnlineQuery(name, variables?)`, for what is only ever asked of the server — see [Online queries](/guide/online-queries)
- `useMutation(name)` — see [Mutations](/guide/mutations)
- `defineQueryHandlers()` and `defineAirplaneStores()` — see [Stores and query handlers](/guide/stores-and-query-handlers)
- `defineMutationHandlers()` — see [Mutation handlers](/guide/mutation-handlers)
- `useSync()` — see [Sync and offline](/guide/sync-and-offline)
- Generated TypeScript types — see [Type generation](/guide/type-generation)

::note
The local database lives in the browser. During server-side rendering `useAirplaneQuery` returns `loading: true` with no data, and the page fills in from IndexedDB once it is in the browser. [`useOnlineQuery`](/guide/online-queries#server-side-rendering) is the one that asks on the server too.
::
